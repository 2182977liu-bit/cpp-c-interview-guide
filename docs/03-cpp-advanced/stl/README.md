## 一、STL 到底由什么组成

很多人背了"六大组件"，但被追问"这六个之间怎么协作"就卡壳。先把它们的关系理清：

| 组件 | 作用 | 一句话理解 |
|---|---|---|
| 容器（container） | 存数据 | 仓库 |
| 迭代器（iterator） | 遍历数据 | 叉车的抓手 |
| 算法（algorithm） | 处理数据 | 操作规范 |
| 仿函数（functor） | 给算法传"策略" | 可调参数的扳手 |
| 适配器（adaptor） | 改造容器/迭代器/仿函数 | 转接头 |
| 分配器（allocator） | 管内存 | 供货商 |

**它们之间的耦合点是迭代器**：算法不认识容器，只认识迭代器；容器不实现算法，只提供迭代器。这套设计的直接好处是 `N` 个容器 + `M` 个算法只需要 `N + M` 份代码，而不是 `N × M`。

面试里问"STL 的设计思想"，标准答案是这三个词：**泛型编程、迭代器解耦、编译期多态**（模板特化而非虚函数派发）。

## 二、容器分类：先建立一张地图

```
序列容器（顺序存储 / 线性结构）
  ├── vector          动态数组，连续内存
  ├── deque           分段连续，双端队列
  ├── list            双向链表
  ├── forward_list    单向链表
  └── array (C++11)   固定大小数组，零开销

关联容器（按 key 组织，自动排序）
  ├── set / multiset
  ├── map / multimap
  └── 底层统一是红黑树

无序关联容器（哈希）
  ├── unordered_set / unordered_multiset
  └── unordered_map / unordered_multimap

容器适配器（不自己存数据，包装别的容器）
  ├── stack           默认包 deque
  ├── queue           默认包 deque
  └── priority_queue  默认包 vector，配堆算法
```

**一个高频送命题**：`stack` 为什么默认用 `deque` 而不是 `vector`？

因为 `deque` 在两端增删都是 O(1) 且不需要整体搬迁，而 `vector` 扩容时要重新分配并移动全部元素；`deque` 的内存虽然分段，但 `stack` 只需要尾部操作，正好避开 `deque` 的短板。另外 `deque` 不会像 `vector` 那样一次性申请大块连续内存。

## 三、vector：最常用的容器，也是追问最狠的容器

### 3.1 三个指针撑起整个 vector

`vector` 的典型实现只有三个指针：

```cpp
T* begin_;   // 数据起始
T* end_;     // 最后一个元素的下一个位置（size 的边界）
T* cap_;     // 已分配内存的末尾（capacity 的边界）
```

- `size() = end_ - begin_`
- `capacity() = cap_ - begin_`

所以 `vector` 的 `size()`、`operator[]`、`back()` 都是常数时间，而且**不需要任何额外成员变量**——这也是 `sizeof(vector<int>)` 通常是 24 字节（64 位下三个指针）的原因。

### 3.2 扩容到底发生了什么

当 `size() == capacity()` 时再插入，`vector` 会：

1. 申请一块更大的连续内存；
2. 把旧元素**逐个搬运**到新内存（元素有 `noexcept` 移动构造时用移动，否则用拷贝）；
3. 析构旧元素，释放旧内存；
4. 插入新元素。

**关键点：扩容的代价不是"多一点内存"，而是"整块搬家"。**

### 3.3 为什么是 2 倍（或 1.5 倍）

这是面试最爱追的点，答"因为快"会被继续追问。真正的理由有两条：

**第一，均摊复杂度**。按固定增量（比如每次 +10）扩容，插入 `n` 个元素的总搬运量是 `O(n²)`；按几何倍数（`k > 1`）扩容，总搬运量收敛为 `O(n)`，均摊到每次插入就是 `O(1)`。

**第二，倍数选多大是内存与时间的权衡**：

| 扩容倍数 | 时间（总搬运次数） | 内存（最多浪费） | 典型实现 |
|---|---|---|---|
| 1.5 倍 | 更多，约 3n | 最多浪费 1/3 | MSVC |
| 2 倍 | 更少，约 2n | 最多浪费 1/2 | libstdc++（GCC） |

所以"2 倍快、1.5 倍省内存"这句话是对的，但只说对了结论。**追问"为什么不能是 3 倍 4 倍"时，答案是：倍数越大，均摊次数越少，但峰值内存浪费越接近 100%，会在内存受限场景下提前 OOM。** 另外还有一条常被忽略的理由：2 倍扩容得到的块大小更容易复用之前释放的块（内存分配器的 best-fit 行为），但这属于实现细节，答出来是加分项。

### 3.4 reserve 与 resize 的区别

```cpp
vector<int> v;
v.reserve(100);   // 只改 capacity：100，size 仍是 0
v.resize(100);    // 改 size：100，并默认构造 100 个元素
```

- `reserve` 只动容量，不构造元素，适合"我知道大概要装多少"的预分配；
- `resize` 会真的创建/销毁元素，`size` 随之变化；
- `reserve` 传的参数比当前 `capacity` 小时，标准**不保证**会缩容（实现通常忽略），要真正释放内存用 `shrink_to_fit()`（C++11，且它是"请求"不是"保证"）。

### 3.5 vector 的三个坑

1. **不能用 `memset` / `memcpy` 处理含非平凡类型的 vector**（比如含 `std::string`）：会破坏内部引用计数，正确做法是赋值或 `std::copy`。
2. **`vector<bool>` 是特化版本**，每个元素压成 1 bit，`operator[]` 返回代理对象而不是 `bool&`，所以不能取地址、不能绑定到 `bool&` 参数。想避免就用 `deque<bool>` 或 `vector<char>`。
3. **在循环里 `push_back` 且持有引用**：扩容后引用悬空。

```cpp
vector<int> v{1, 2, 3};
int& r = v[0];
v.push_back(4);      // 可能触发扩容
cout << r;           // 未定义行为：r 指向已释放的旧内存
```

## 四、deque 与 list：两个容易被问倒的"非常规"容器

### 4.1 deque 的"分段连续"

`deque` 不是一整块连续内存，而是**一组固定大小的块（chunk）+ 一个中控数组（map）**：

```
中控数组:  [ ptr0 ][ ptr1 ][ ptr2 ][ ptr3 ] ...
              │       │       │
块(512字节): [元素...][元素...][元素...]
```

- 头部插入：在第一个块里往前放；块用完了就在中控数组前面挂一个新块，`O(1)`；
- 尾部插入：同理，`O(1)`；
- 中间插入/删除：需要移动元素，`O(n)`；
- 随机访问：`operator[]` 需要先算"第几个块 + 块内偏移"，是两次间接寻址，所以比 `vector` 慢（但仍属常数时间）。

**这就是"deque 支持 O(1) 双端插入、但比 vector 慢一点"的底层原因。**

### 4.2 list 与 vector 的真实取舍

| 维度 | vector | list |
|---|---|---|
| 内存 | 连续，无额外开销 | 每个节点两个指针，64 位下 16 字节额外开销 |
| 随机访问 | O(1) | O(n) |
| 尾部插入 | 均摊 O(1) | O(1)（有 end 迭代器） |
| 中间插入/删除 | O(n)（要搬元素） | O(1)（但要先 O(n) 找到位置） |
| 缓存友好性 | 极好（预取命中） | 差（节点分散在堆上） |
| 迭代器失效 | 扩容/插入/删除都可能失效 | 仅被删除的那个失效 |

**面试时的加分回答**："实际项目中 `list` 很少用，因为链表虽然插入是 O(1)，但找到插入位置的遍历是 O(n)，且缓存不友好；真正需要频繁中间插入的场景，通常用 `vector` + 批量重建，或者用 `std::list` 的替代品（如侵入式链表 `boost::intrusive::list`）来省掉节点内的指针开销。"

## 五、map 与 unordered_map：有序与无序的取舍

### 5.1 底层结构

- `std::map` / `std::set`：**红黑树**。自平衡二叉搜索树,插入/删除/查找都是 `O(log n)`，中序遍历天然有序（所以支持 `lower_bound`、范围查询）。
- `std::unordered_map` / `unordered_set`：**哈希表**（桶数组 + 桶内链表），平均 `O(1)`，最坏 `O(n)`。

### 5.2 哈希表的关键参数

```cpp
unordered_map<string, int> m;
m.max_load_factor();   // 默认 1.0
m.bucket_count();      // 当前桶数量
m.load_factor();       // size / bucket_count
```

当 `load_factor() > max_load_factor()` 时触发 **rehash**：桶数量增长（通常是接近 2 倍的质数），**所有元素重新计算桶位置**。

`rehash` 的代价：
- 时间是 `O(n)`（要重新分配所有节点）；
- **所有迭代器失效**；
- 但**元素的引用和指针仍然有效**（标准明确保证 rehash 不会让元素的引用失效，因为节点本身没搬家，只是桶的挂链变了）。

这条"迭代器失效但引用有效"的差异，是 `unordered_map` 最容易被追问的细节。

### 5.3 怎么选

| 场景 | 选择 |
|---|---|
| 需要按 key 排序、范围查询（如 `for (auto it = m.lower_bound(k); ...)`） | `map` |
| 只要快速查找、插入，不关心顺序 | `unordered_map` |
| key 是整数且范围小 | 考虑直接开数组 / `vector` 当查找表 |
| 需要稳定的最坏情况（防哈希碰撞攻击） | `map`（红黑树最坏也是 `O(log n)`） |

`unordered_map` 的两条实用建议：`reserve(n)` 预留桶数避免多次 rehash；自定义哈希函数时注意"哈希质量差 + 攻击者可控 key"会导致退化成链表。

## 六、allocator：容器的"供货商"

`allocator` 把**内存分配**和**对象构造**拆成两步：

```cpp
allocator<T> a;
T* p = a.allocate(n);        // 只分配原始内存，不构造
a.construct(p, args...);     // 在 p 上构造对象（C++17 起用 allocator_traits）
a.destroy(p);                // 析构
a.deallocate(p, n);          // 释放
```

**为什么需要它**：容器只负责"逻辑结构"，不知道内存该从哪来。把分配策略抽出来之后，你可以换成内存池、共享内存、带统计的分配器，而容器代码一行不用改。`std::pmr`（C++17 的 polymorphic memory resource）就是这个思想的现代版本。

面试如果问"allocator 有什么实际用途"，答这三条最实在：内存池降低分配开销、对齐控制（如 SIMD 需要 32/64 字节对齐）、嵌入式场景下的固定内存池避免碎片。

## 七、迭代器失效：面试官最爱在这里挖坑

先给结论表，再讲原因：

| 容器 | 插入导致的失效 | 删除导致的失效 |
|---|---|---|
| `vector` | 扩容：**全部失效**；未扩容：插入点及之后失效 | 删除点及之后失效 |
| `deque` | 中间插入：全部失效；两端插入：迭代器失效但**引用/指针仍有效** | 中间删除：全部失效；两端删除：仅被删元素的失效 |
| `list` | 不失效 | 仅被删除元素的迭代器失效 |
| `map` / `set` | 不失效 | 仅被删除元素的迭代器失效 |
| `unordered_*` | rehash：**迭代器全部失效，引用/指针有效** | 仅被删除元素的迭代器失效 |

### 7.1 必背的两个正确写法

```cpp
// 错误：erase 之后 it 已失效，再 ++ 是未定义行为
for (auto it = v.begin(); it != v.end(); ++it)
    if (*it == target) v.erase(it);

// 正确：erase 返回下一个有效迭代器
for (auto it = v.begin(); it != v.end(); )
    if (*it == target) it = v.erase(it);
    else ++it;
```

```cpp
// list / map / set 也可以这样，但它们是"删除当前不影响其他"
for (auto it = m.begin(); it != m.end(); )
    if (it->second < 0) it = m.erase(it);
    else ++it;
```

### 7.2 为什么 vector 的删除会让"之后"的迭代器失效

因为 `erase` 的实现是把后面的元素整体前移一位，被删位置之后的每个元素都换了地址，指向旧地址的迭代器自然失效。**理解这一点，整张表就不用背了**：凡是"元素会搬家"的容器（vector、deque 中间操作），失效范围就大；凡是"节点地址固定"的容器（list、红黑树、哈希节点），失效范围就小。

## 八、push_back 与 emplace_back

```cpp
vector<string> v;
v.push_back("hello");        // 先构造临时 string，再移动/拷贝进容器
v.emplace_back("hello");     // 直接在容器内存上构造，省一次移动
```

- `emplace_back` 用完美转发把参数直接交给元素的构造函数，**理论上少一次移动构造**；
- 但当参数已经是同类型对象时（`v.push_back(s)` 且 `s` 是 `string`），两者差别很小；
- `emplace_back` 的隐患：因为它允许隐式构造，某些情况下会绕过 `explicit` 的意图，或者匹配到你没预料到的构造函数。**对 `vector<int>` 这类，`emplace_back(1)` 和 `push_back(1)` 没区别。**

面试追问"emplace_back 一定更快吗"——答案是不一定，取决于元素类型和实参形式，但在"需要用参数构造元素"的场景（如 `emplace_back(a, b)` 构造 `pair`）优势明确。

## 九、复杂度总表

| 容器 | 随机访问 | 尾部插 | 头部插 | 中间插 | 查找 | 有序 |
|---|---|---|---|---|---|---|
| `vector` | O(1) | 均摊 O(1) | O(n) | O(n) | O(n) | 否 |
| `deque` | O(1) | O(1) | O(1) | O(n) | O(n) | 否 |
| `list` | O(n) | O(1) | O(1) | O(1)* | O(n) | 否 |
| `map`/`set` | — | — | — | O(log n) | O(log n) | 是 |
| `unordered_map` | — | — | — | 平均 O(1) | 平均 O(1) | 否 |

\* `list` 的中间插入是 O(1)，但**找到插入位置**是 O(n)，面试时要把这半句补上。

## 十、面试真题

### 真题 1：vector 为什么按 2 倍扩容？

答三层：① 几何增长把 n 次插入的总搬运量从 `O(n²)` 压到 `O(n)`，均摊 O(1)；② 2 倍是 libstdc++ 的选择，MSVC 用 1.5 倍，1.5 倍内存浪费更少但搬运更多；③ 倍数不能无限大，因为峰值内存浪费会逼近 100%。

### 真题 2：vector 的 size 和 capacity 有什么区别？

`size` 是已构造的元素个数，`capacity` 是已分配的可用槽位数。`size <= capacity` 恒成立。`reserve` 改 capacity，`resize` 改 size。

### 真题 3：map 和 unordered_map 的底层实现与区别？

`map` 是红黑树，`O(log n)`，有序，支持范围查询，最坏情况稳定；`unordered_map` 是哈希桶，平均 `O(1)`，无序，可能因 rehash 出现 `O(n)` 的插入，最坏 `O(n)`。

### 真题 4：迭代器失效有哪些场景？

按"元素是否搬家"分类：`vector` 扩容全部失效；`deque` 中间操作全部失效、两端操作引用仍有效；`list`/`map`/`set` 仅被删元素失效；`unordered_map` rehash 时迭代器失效但引用有效。修复方式：用 `erase` 的返回值接住下一个迭代器。

### 真题 5：push_back 和 emplace_back 的区别？

`emplace_back` 在容器内存上就地构造，省一次移动构造，靠完美转发实现；实参已是同类型对象时差别很小。

### 真题 6：unordered_map 的 rehash 是什么？如何避免？

当 `load_factor` 超过 `max_load_factor`（默认 1.0）时重建桶数组并重新挂链，时间 `O(n)`。避免方式：`reserve(n)` 预留桶数、调大 `max_load_factor`、或换 `map`。

### 真题 7：deque 为什么两端插入是 O(1)？

因为它是"分块 + 中控数组"结构，两端插入只需在当前端块里写入或挂一个新块，不需要整体搬迁。

### 真题 8：stack 为什么默认基于 deque？

`deque` 两端操作 O(1) 且不需要大块连续内存，避开了 `vector` 扩容时整体搬家的代价。

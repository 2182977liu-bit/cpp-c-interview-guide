### 1. 互斥锁与自旋锁

**场景还原**："自旋锁忙等待、互斥锁睡眠"是常识答案。追问"性能拐点在哪""单核为什么不能用自旋锁""自旋锁会活锁吗"，考的是这个判断：**临界区执行时间 vs 上下文切换开销**。

#### 三句话版本

**自旋锁**在用户态死循环检测锁状态（忙等待）：拿到锁的瞬间延迟极低，但等待期间 CPU 空转。**互斥锁**经系统调用让拿不到锁的线程睡眠：CPU 可干别的，但唤醒要两次上下文切换（用户态→内核态→用户态），延迟高。判断标准：临界区执行时间短于两次上下文切换开销（通常 1-10μs）→ 自旋锁划算；否则互斥锁。

#### 展开讲

**自旋锁怎么工作**。核心是一个原子变量（如 std::atomic_flag）：加锁时 test_and_set 原子操作尝试把标志 0→1，失败说明别人持锁，while 循环不断重试；解锁清零标志。全程无系统调用、不睡眠、零上下文切换开销。代价：等待期间 CPU 核心被完全占住，干不了任何有用的事。

**互斥锁怎么工作**。std::mutex 加锁失败时经系统调用（Linux 上是 futex）把线程放进等待队列并睡眠；持锁线程解锁时内核唤醒等待队列中的一个线程。过程涉及用户态↔内核态切换（保存/恢复寄存器、切页表等），开销约 1-10μs。好处：睡眠期间 CPU 核心可执行其他线程。

**性能拐点**。临界区只做一两次内存读写（几十纳秒）→ 自旋锁的忙等待远小于互斥锁两次切换的开销，自旋锁更优。临界区要做 IO 或复杂计算（几十微秒以上）→ 自旋锁让等待线程白白烧 CPU，互斥锁睡眠反而高效。经验值：临界区超过 10-20μs 就该用互斥锁。

**单核为什么不能用自旋锁**。单核只有一个执行流：线程 A 持锁、线程 B 自旋等待——B 占着唯一核心不放，A 没机会运行来释放锁，形成类死锁。只有可抢占内核（时间片到强制切换）或 B 主动 yield() 才能勉强用，但此时自旋锁的优势已荡然无存。

#### 高频追问

**Q：自旋锁会活锁吗？**
会。多线程同时自旋竞争同一把锁可能出现"惊群"——全在自旋、谁也拿不到。对策：随机退避（失败后随机等一小段再试）、票据锁（ticket lock）保公平、MCS 锁减缓存行争用。

**Q：自旋次数上限怎么定？**
工程常用"自适应自旋"：先自旋一定次数（约上下文切换开销的 1.5-2 倍），仍拿不到就退化成互斥锁睡眠。Java 的 synchronized 与 Linux 内核 mutex_lock 都是这种混合策略。

**Q：C++ 标准库有自旋锁吗？**
没有专门的类，但可用 std::atomic_flag 的 test_and_set + clear 自己实现；C++20 新增 atomic_flag::wait() 与 notify_one() 可实现更高效等待。实际项目需要自旋锁时通常用平台实现（如 Linux 的 pthread_spinlock_t）。

**Q：读写锁与自旋/互斥锁什么关系？**
读写锁是更高层抽象：多读者可同时持锁、写者独占。其底层可基于自旋锁（读多写少 + 短临界区）或互斥锁（长临界区）。C++ 标准库的 std::shared_mutex 底层通常基于互斥锁实现。

### 2. select/poll/epoll

**场景还原**："说一下 select、poll、epoll 的区别"——答"epoll 性能最好"只值零分。追问"为什么好""好在哪""什么场景 select 反而更合适"，考的是内核 IO 多路复用的实现机制：**数据结构、通知方式、内核态到用户态的拷贝**。

#### 三句话版本

三者都让单线程同时监视多个 fd 的就绪状态。核心差异：**select** 用位图、1024 上限、每次 O(n) 轮询；**poll** 用数组、去掉数量上限、但仍 O(n) 遍历；**epoll** 用红黑树 + 就绪链表 + 事件回调，只返回活跃 fd——大量连接时性能碾压前两者。

#### 全维度对照

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| 数据结构 | 位图 fd_set | pollfd 结构体数组 | 红黑树 + 就绪链表 |
| fd 数量限制 | 默认 1024（FD_SETSIZE） | 无硬性限制（受 ulimit 约束） | 无硬性限制 |
| 每次调用开销 | 重设 fd_set + 拷入内核 + 遍历全部 fd | 拷入整个数组 + 遍历全部 fd | 只取就绪链表，无需遍历 |
| 就绪通知 | 返回后需遍历所有 fd 找就绪的 | 同 select | epoll_wait 直接返回就绪 fd 列表 |
| 时间复杂度 | O(n) | O(n) | O(活跃连接数) |
| 触发模式 | 仅水平触发（LT） | 仅 LT | 支持 LT 与边缘触发（ET） |
| 跨平台 | 是（POSIX） | 是（POSIX） | 否（Linux 特有） |

**为什么 epoll 在海量连接下碾压 select/poll**。select/poll 每次调用都要把所有监控 fd 从用户态拷进内核，内核遍历所有 fd 查就绪状态，返回后用户态再遍历一遍——1 万连接、只有 10 个活跃，也要遍历 1 万次，这就是 O(n) 的代价。epoll 的设计完全不同：epoll_ctl 注册 fd 时挂进内核红黑树，此后无需重复拷贝；fd 就绪时内核经回调把它加入就绪链表；epoll_wait 只查就绪链表——不管总连接数多大，开销只与活跃连接数成正比。

**LT 与 ET 的区别**。水平触发（LT，默认）：fd 处于就绪状态时 epoll_wait 每次都返回它——编程简单，不及时处理会反复通知。边缘触发（ET）：只在 fd 状态变化时通知一次——必须一次性读完所有数据（非阻塞 IO + 循环读到 EAGAIN），否则数据丢失。ET 减少 epoll_wait 返回次数，高并发性能更好，但编程复杂度更高。

#### 高频追问

**Q：连接数少的时候用哪个？**
几十到几百连接时三者性能差异不大。需要跨平台（macOS/Windows）只能 select/poll——epoll 是 Linux 特有（macOS 用 kqueue、Windows 用 IOCP）。结论：连接少 + 跨平台 → select/poll；Linux + 高并发 → epoll。

**Q：epoll 的 mmap 是怎么回事？**
早期流传"epoll 用 mmap 让内核与用户态共享内存避免拷贝"。实际现代 Linux 内核实现中，epoll_wait 返回就绪事件仍有一次内核→用户态拷贝（copy_to_user），但只拷就绪 fd（而非全部）、数据量极小，开销可忽略。真正省的是"注册时一次拷贝 vs 每次调用全量拷贝"。

**Q：select 的 1024 限制能改吗？**
可以改 FD_SETSIZE 宏重编译，但不推荐——fd_set 是定长位图，改大了栈空间开销也涨。需要大量 fd 直接用 poll 或 epoll。

**Q：ET 模式为什么必须配非阻塞 IO？**
ET 只通知一次，必须循环读到 EAGAIN 才能确认数据读完。fd 若是阻塞的，最后一次 read 会卡住（没数据了还在等）——整个事件循环卡死。ET + 非阻塞 IO 是固定搭配。

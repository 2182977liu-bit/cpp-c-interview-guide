### 1. STL 容器分类选型

**场景还原**："STL 容器了解哪些？"——只报名字没有区分度。得分点在于三大分类的底层结构差异与选型依据：什么场景用什么容器、为什么。

#### 三句话版本

STL 容器 = 三大类 + 一类适配器：

- **顺序容器**：vector（动态数组）、deque（分段数组）、list（双向链表）、forward_list（单向链表）、array（固定数组）——按插入顺序存
- **关联容器**：map/multimap、set/multiset——红黑树底层，自动有序，O(log n)
- **无序容器**：unordered_map/unordered_multimap、unordered_set/unordered_multiset——哈希表底层，无序，平均 O(1)
- **容器适配器**：stack、queue、priority_queue——不是独立容器，是底层容器的接口封装

#### 展开讲

**顺序容器——按插入顺序存储**，核心差异在内存布局与操作效率：

- vector：连续内存，随机访问 O(1)，尾插均摊 O(1)，中间插 O(n)。最常用、缓存最友好
- deque：分段连续，两端插 O(1)，随机访问 O(1)，中间插 O(n)。适合两端操作
- list：双向链表，已知位置插删 O(1)，不支持随机访问。迭代器不失效
- forward_list：单向链表，比 list 省一个指针，只能单向遍历
- array：编译期定长，零开销替代 C 数组，不能扩容

**关联容器——自动有序**，底层全是红黑树：

- map：键值对、键唯一。需要有序遍历或范围查询时用
- set：只存键、自动去重排序。判断存在且要求有序时用
- multimap/multiset：允许重复键

**无序容器——哈希查找**，底层哈希表、不保证顺序：

- unordered_map：键值对，平均 O(1) 查/插。只要快、不要有序时用
- unordered_set：只存键，平均 O(1) 判存在

**容器适配器——接口封装**：

- stack：后进先出，默认底层 deque
- queue：先进先出，默认底层 deque
- priority_queue：堆，默认底层 vector

**快速选型表**

| 需求 | 推荐容器 |
| --- | --- |
| 随机访问 + 尾部增删 | vector |
| 两端频繁增删 | deque |
| 中间频繁增删（已知位置） | list |
| 有序键值查找/范围查询 | map |
| 快速查找（不需要有序） | unordered_map |
| 去重 + 有序 | set |
| 去重 + 快速判存在 | unordered_set |

#### 高频追问

**Q：vector 和 deque 怎么选？**
默认 vector——内存完全连续、缓存性能最好、可经 data() 拿裸指针喂 C API。只有频繁头部插删才考虑 deque。

**Q：map 和 unordered_map 怎么选？**
要有序（范围查询、按序遍历）→ map；只要快 → unordered_map。数据量小时 map 可能更快（红黑树常数小），量大时 unordered_map 优势明显。

**Q：什么时候才用 list？**
现代 C++ 里 list 场景极少：仅两种——中间频繁插删且已持有迭代器；插删后其他迭代器不失效。其余场景 vector 几乎总是更快（缓存局部性优势太大）。

**Q：适配器和容器的区别？**
适配器不是独立数据结构，只是限制底层容器接口：stack 禁随机访问、只暴露 push/pop/top，底层默认 deque、可换 vector 或 list。适配器的价值是语义约束——告诉使用者"这里只能后进先出"。

### 2. allocator

**场景还原**："allocator 是干什么的？"——答"分配内存"只答了四分之一。得分点是讲全它的**四个职责**，以及"为什么要把内存管理从容器中抽出来"。

#### 三句话版本

Allocator 是 STL 的内存管理组件，核心作用是把**容器的数据结构逻辑**与**底层内存操作**解耦。四个职责：allocate 分配原始内存、deallocate 释放内存、construct 在内存上构造对象、destroy 析构对象但不释放内存。经模板参数注入不同 allocator，不改容器代码即可切换内存策略。

#### 展开讲

**四大核心职责**：

- `allocate(n)`：分配容纳 n 个对象的原始内存，不调构造
- `deallocate(p, n)`：释放之前分配的内存，不调析构
- `construct(p, args...)`：在已分配地址上用 placement new 构造对象
- `destroy(p)`：调对象析构，但不释放内存

这四步把"内存生命周期"与"对象生命周期"彻底分开：容器可以先占一大块内存（reserve），需要时再逐个构造对象，不必每次都 new/delete。

**设计理念：策略模式解耦**。容器只管数据结构（怎么组织元素），allocator 只管内存（从哪拿、怎么还）。两者经模板参数绑定、互不侵入——想换内存策略（堆分配 → 内存池），换 allocator 类型即可，容器代码零改动。

**rebind 机制**。容器内部不只分配用户类型：`list<int>` 内部要分配的是节点 `_Node<int>` 而非 int。rebind 让 `allocator<int>` 能"重绑"为 `allocator<_Node<int>>`，容器内部辅助结构共用同一套内存策略。C++11 后由 allocator_traits 简化了这套机制。

#### 高频追问

**Q：为什么不直接用 new/delete？**
new/delete 把内存分配与对象构造绑死，无法分开控制。容器经常需要"先占内存、稍后构造"（如 vector 的 capacity > size），必须拆开两步——allocator 正是干这个的。

**Q：什么时候需要自定义 allocator？**
四个典型场景：内存池（降 malloc/free 开销）、共享内存（进程间通信）、GPU 内存（异构计算）、内存监控（调试泄漏）。日常默认 allocator 够用，性能敏感或特殊硬件才需要自定义。

**Q：自定义 allocator 有什么坑？**
四个：异常安全（allocate 失败要抛 bad_alloc）；对齐要求（alignas）；容器交换/移动时的传播语义（propagate_on_container_swap 等 traits）；线程安全（多线程下分配器状态）。

**Q：C++17 对 allocator 改了什么？**
废弃了 construct/destroy 成员，统一由 allocator_traits 代劳。自定义 allocator 只需提供 allocate/deallocate，其余由 traits 默认实现——编写难度大幅下降。

### 3. 迭代器失效

**场景还原**："什么情况下迭代器失效？vector 和 list 的失效规则差在哪？"——知道"删除后失效"只是常识。各容器的具体规则、插入时会不会失效，才是得分点。失效的根因一句话：**迭代器指向的内存地址不再有效**。

#### 三句话版本

迭代器失效 = 指向的地址失效（类似悬垂指针），继续使用即未定义行为——可能崩，也可能读垃圾数据。失效三大根因：内存重分配（vector 扩容）、元素位置移动（vector 中间删除致后续前移）、节点销毁（list/map 删节点）。规则差异取决于底层数据结构：**连续内存（vector）牵一发动全身，链表/树结构（list/map）只影响被操作的节点**。

#### 分容器规则

**vector / string（连续内存）**

- 插入：触发扩容（size 超过 capacity）→ **全部**迭代器失效（整块内存搬了新地址）；没扩容 → 插入点之后的失效（元素后移）
- 删除：被删元素及其之后的全部失效（后续前移，地址变了）；之前的不受影响

**deque（分段连续内存）**

- 插入：首尾插入不失效迭代器（引用可能失效）；中间插入 → 全部失效
- 删除：首尾删除只失效被删元素；中间删除 → 全部失效

**list / forward_list（链表）**

- 插入：**永不失效**任何迭代器（新节点不影响已有节点地址）
- 删除：只失效被删元素，其余完全不受影响

**set / map（红黑树）**

- 插入：**永不失效**
- 删除：只失效被删元素

**unordered_set / unordered_map（哈希表）**

- 插入：触发 rehash（负载因子超阈值）→ 全部失效；未触发则不失效
- 删除：只失效被删元素

#### 高频追问

**Q：循环中删除 vector 元素的正确姿势？**
错误示范：`for(auto it = v.begin(); it != v.end(); ++it) { if(条件) v.erase(it); }`——erase 后 it 已失效，再 ++it 是未定义行为。正确写法：`it = v.erase(it)`，用返回的下一个有效迭代器，不满足条件才 ++it。更优雅的是 erase-remove 惯用法：`v.erase(std::remove_if(v.begin(), v.end(), 条件), v.end())`，一次遍历搞定。

**Q：为什么 vector 扩容会让全部迭代器失效？**
vector 内存连续：扩容时 new 更大内存、把元素全部拷贝/移动过去、delete 旧内存。所有迭代器本质是指向旧内存的指针，旧内存一释放就集体变悬垂。提前 reserve 足够容量可避免扩容型失效。

**Q：多线程下怎么处理迭代器失效？**
STL 容器本身非线程安全——多线程同时读写同一容器，抛开迭代器失效也是数据竞争（UB）。方案：mutex 保护全部读写；读写锁（多读单写）；或避免遍历时改容器——先收集待删元素、遍历完统一删。

**Q：怎么调试迭代器失效？**
GCC 调试模式（-D_GLIBCXX_DEBUG）运行时校验迭代器有效性，失效后使用直接抛异常而非静默 UB；MSVC Debug 默认开迭代器调试；AddressSanitizer（-fsanitize=address）也能抓到部分失效型内存错误。

### 4. map 与 unordered_map

**场景还原**："一个有序一个无序"只是表层。追问"底层结构怎么决定性能差异""什么时候选谁""哈希冲突怎么处理"，考的是对两种数据结构的理解深度。

#### 三句话版本

**map** 底层红黑树：元素按 key 自动排序，增删查全 O(logN)。**unordered_map** 底层哈希表：无序，增删查平均 O(1)、最坏退化 O(n)。选型：要有序遍历或范围查询用 map，只关心单点查找速度用 unordered_map。

#### 全维度对照

| 维度 | map | unordered_map |
| --- | --- | --- |
| 底层结构 | 红黑树（自平衡 BST） | 哈希表（桶数组 + 链表） |
| 元素顺序 | 按 key 升序 | 无序 |
| 查找/插入/删除 | O(logN) 稳定 | O(1) 平均，O(n) 最坏 |
| key 要求 | 必须支持 <（或自定义比较器） | 必须支持 hash 与 == |
| 内存开销 | 每节点 3 指针 + 颜色位，紧凑 | 桶数组有空槽、预留扩容空间，整体更大 |
| 迭代器失效 | 插入不失效；删除只失效被删元素 | rehash 时全部失效 |

**怎么选**：要按 key 排序遍历、范围查询（lower_bound/upper_bound）、或 key 类型没有好哈希函数 → map；只做点查、插入频繁、元素量大且哈希分布均匀 → unordered_map。

#### 高频追问

**Q：unordered_map 的哈希冲突怎么处理？**
链地址法：同桶元素串成链表。插入挂链尾，查找先哈希定位桶、再遍历链表比 key。冲突越多链越长，性能越差。

**Q：为什么最坏是 O(n)？**
极端情况全部 key 哈到同一桶——整表退化成一条链表，查找变线性扫描。工程上靠好的哈希函数与合理负载因子规避。

**Q：负载因子和 rehash 是什么？**
负载因子 = 元素数 / 桶数，衡量哈希表拥挤度。STL 默认阈值 1.0，超过即触发 rehash：分配更大桶数组、全部元素重新哈希重排。rehash 是 O(n) 的一次性开销，之后查找恢复 O(1)。预知元素量可用 reserve() 预分配，避免中途 rehash。

**Q：多线程场景怎么选？**
两者都非线程安全。map 结构稳定、适合读多写少配合 shared_mutex；unordered_map 并发写风险高（rehash 让全部迭代器失效），要么分桶加锁、要么上 TBB 的 concurrent_unordered_map。

### 5. 容器底层实现

**场景还原**："map、deque、list 底层怎么实现？"——报"红黑树、数组、链表"只是开场。追问"deque 的随机访问怎么做到 O(1)""list 为什么缓存性能差"才见深度。

#### 三句话版本

**map**：红黑树（自平衡 BST），键有序，增删查全 O(log n)；unordered_map 则是哈希表、无序、平均 O(1)。**deque**：分段连续存储——一个中控数组（map）指向多个定长缓冲区块；两端插 O(1)，随机访问 O(1)（块索引 + 块内偏移两次计算）。**list**：双向链表，节点存前驱/后继/数据；已知位置插删 O(1)，定位靠遍历，缓存不友好。

#### 展开讲

**map（红黑树）**。红黑树保证最长路径不超过最短路径两倍，所有操作 O(log n)；键自动有序（按 < 或自定义比较器）；插入/删除不使其他迭代器失效——树结构的天然优势。unordered_map 用哈希表：桶+链表（或桶+红黑树），平均 O(1) 最坏 O(n)，rehash 时全部迭代器失效。

**deque（分段连续存储）**。核心结构：指针数组（中控 map），每指针指向一块定长连续缓冲区。push_front/push_back 只在当前块前后填充，块满就分配新块、在中控 map 里加一个指针。随机访问：先算目标在第几块（偏移 / 块大小），再算块内位置（偏移 % 块大小），两次除法定位——O(1)。中间插入需移动元素，O(n)。

**list（双向链表）**。每节点独立分配、靠前驱/后继串联。已知迭代器位置时插删只改指针，O(1)；定位第 n 个元素必须从头遍历，O(n)。节点散布堆上、缓存不友好（cache miss 多）——这是 list 在现代硬件上性能差的主因。插删不使其他迭代器失效。

**选型对照**

| 维度 | map | deque | list |
| --- | --- | --- | --- |
| 底层结构 | 红黑树 | 分段连续数组 | 双向链表 |
| 随机访问 | 不支持 | O(1) | 不支持 |
| 两端插入 | O(log n) | O(1) | O(1) |
| 中间插入 | O(log n) | O(n) | O(1)（已知位置） |
| 迭代器失效 | 删除当前才失效 | 头尾插入不失效，中间插入全失效 | 删除当前才失效 |
| 缓存友好 | 差 | 较好 | 差 |

#### 高频追问

**Q：deque 中间插入为什么比 list 慢？**
deque 中间插入要移动元素维持块内连续性，平均搬 n/2 个、还可能跨块；list 只改两个指针、恒定 O(1)。但插入不频繁时，deque 的缓存友好带来的遍历优势远超 list。

**Q：什么时候才该用 list？**
两种情况：中间位置频繁插删且已持迭代器；插删后迭代器/指针/引用不失效。除此之外，现代 C++ 中 deque 甚至 vector 几乎总比 list 快——缓存局部性的优势太大了。

**Q：map 和 unordered_map 怎么选？**
键要有序（范围查询、按序遍历）→ map；只要快 → unordered_map。unordered_map 平均更快但最坏差、rehash 全失效；map 稳定 O(log n)、迭代器几乎不失效。

**Q：deque 能完全替代 vector 吗？**
不能。deque 内存分段连续，无法直接喂给要连续内存的 C API；vector 保证完全连续、可 data() 拿裸指针。且 vector 的缓存性能比 deque 更好（完全连续 vs 分段连续）。

### 6. rehash 机制

**场景还原**："unordered_map 什么时候 rehash？"——答"元素多了就扩容"太糙。追问"负载因子怎么算""rehash 复杂度多少""迭代器会不会失效""reserve 和 rehash 区别"才是完整考点。

#### 三句话版本

unordered_map 底层是哈希表（桶数组 + 链表/红黑树）。**负载因子 = size() / bucket_count()**，衡量桶的拥挤度。插入导致负载因子超过 max_load_factor()（默认 1.0）即自动 rehash：分配更大桶数组、所有元素重新哈希重排，O(n)。rehash 后**全部迭代器失效**，但元素的引用与指针不失效（节点式容器，节点本体不搬移）。可提前 reserve(n) 预分配，避免插入过程中多次 rehash 造成的性能抖动。

#### 展开讲

**负载因子——触发条件**。负载因子 = 元素数 / 桶数。因子越高，桶内链越长，查找从 O(1) 退化到 O(n)。因此 unordered_map 设了上限 max_load_factor()（默认 1.0）：每次插入后若 load_factor() 超限，自动 rehash。

**rehash 的四步流程**：

1. 分配更大的新桶数组（通常约 2 倍，取下一个素数）
2. 遍历旧桶的所有节点
3. 对每个节点的 key 重算 hash(key) % new_bucket_count，挂到新桶
4. 释放旧桶数组

全程 O(n)——这正是 unordered_map 插入是"**均摊 O(1)**"而非"严格 O(1)"的原因：绝大多数插入 O(1)，偶尔一次插入触发 O(n) rehash。

**迭代器失效规则**。rehash 后全部迭代器失效；但元素的引用与指针**不失效**——unordered_map 是节点式容器，rehash 只是把节点从旧桶摘下挂到新桶，节点本体地址不变。对比 vector：扩容后连引用也失效。

**reserve 与 rehash 的区别**。rehash(n)：直接把桶数设为至少 n。reserve(n)：从元素数出发，保证插入 n 个元素前不触发 rehash，内部调用 rehash(ceil(n / max_load_factor()))。已知要插多少元素时，用 reserve 更直观。

#### 高频追问

**Q：默认 max_load_factor 为什么是 1.0？**
空间与时间的权衡：因子越小桶越空、查找越快但内存浪费越多。1.0 意味着平均每桶一个元素，是较平衡的选择。Java HashMap 默认 0.75，更偏性能。

**Q：rehash 会改变元素相对顺序吗？**
会。rehash 后元素在桶中的分布完全重算，遍历顺序改变。这也是"无序"含义的一部分——不保证任何遍历顺序，两次遍历之间若发生过 rehash，顺序都可能不同。

**Q：怎么避免 rehash 的性能抖动？**
预估元素数量，插入前 reserve(n)——一次性分配够桶，后续插入都不触发 rehash。实时系统或延迟敏感场景这是必做优化。

**Q：unordered_map 和 map 怎么选？**
要有序遍历或范围查询 → map（红黑树 O(log n)）；只要快 → unordered_map（哈希表均摊 O(1)）。数据量小时 map 可能更快（常数小），量大时 unordered_map 优势明显。

### 7. vector 底层与扩容

**场景还原**："说一下 vector 的底层实现，扩容时发生了什么？"——C++ 面试出场率最高的题之一。答"动态数组、2 倍扩容"只是皮毛，三个指针的含义与"为什么扩容后全部迭代器失效"才是得分点。

#### 三句话版本

vector 底层一块连续内存，靠三个指针管理：`_start` 指首元素，`_finish` 指最后一个元素的下一位置，`_end_of_storage` 指已分配内存的末尾。当 size() == capacity() 时再插入即触发扩容——分配更大内存（通常 2 倍）、搬迁旧元素、释放旧内存。

#### 展开讲

**三个指针的含义**（所有操作围绕它们展开）：

- `_start`：指向数组首元素，begin() 返回它
- `_finish`：指向最后一个有效元素的下一位置，end() 返回它；`size() = _finish - _start`
- `_end_of_storage`：指向已分配内存块的末尾；`capacity() = _end_of_storage - _start`

当 `_finish == _end_of_storage`——空间用尽，下一次 push_back 触发扩容。

**扩容的完整流程**：

1. 分配新内存，通常是原来的 2 倍（GCC libstdc++）；MSVC 用 1.5 倍
2. 旧元素逐个拷贝或移动到新内存（元素有 noexcept 移动构造时优先移动）
3. 释放旧内存
4. 三个指针指向新内存

全程旧内存地址失效——所有指向旧元素的迭代器、指针、引用全部失效。

**时间复杂度**：

- 随机访问：O(1)——连续内存直接算偏移
- 尾部插入：均摊 O(1)——单次扩容 O(n)，但扩容频率随容量指数增长而降低
- 中间插入/删除：O(n)——需移动后续全部元素

#### 高频追问

**Q：为什么选 2 倍扩容而不是固定增量？**
固定增量（每次 +100）的分摊复杂度是 O(n)——总拷贝次数与元素数量成正比；倍数扩容的分摊复杂度 O(1)——每个元素平均只被拷贝常数次。

**Q：reserve 和 resize 的区别？**
reserve(n) 只分配内存不创建元素——改 capacity 不改 size；resize(n) 实际创建或销毁元素——size 和 capacity 都可能变。预知数量时用 reserve 避免多次扩容。

**Q：扩容后能把多余内存还回去吗？**
C++11 提供 shrink_to_fit()——请求把 capacity 缩到 size，注意是非绑定请求、实现可忽略。经典做法还有 `vector<int>(v).swap(v)`。

**Q：vector 和 deque 的扩容策略差异？**
deque 不做整体搬迁：分段连续内存（多个定长 buffer），扩容只加一个新 buffer、不拷贝已有元素——所以 deque 头尾插入都不会使已有元素的引用失效。

### 8. push_back 与 emplace_back

**场景还原**："emplace_back 更高效"人人会说，追问"高效在哪""什么时候 push_back 反而更好""扩容时 emplace_back 还能省吗"就露怯了。这道题考 STL 内存模型与 C++11 完美转发的结合：**在哪构造**与**怎么传参**。

#### 三句话版本

push_back 接收**已构造好的对象**（左值或右值），靠拷贝/移动搬进容器；emplace_back 接收**构造函数的参数**，经完美转发直接在容器尾部内存上原地构造——省掉临时对象与一次拷贝/移动。一句话：push_back 是"做好了搬进去"，emplace_back 是"直接在里面做"。

#### 展开讲

**底层机制差异**。push_back 有两个重载：`push_back(const T&)` 与 `push_back(T&&)`——接收完整对象，左值触发拷贝构造、右值触发移动构造。不管哪种，容器外先有对象、再"搬"进容器内存。emplace_back 是变参模板 `emplace_back(Args&&... args)`：任意数量参数经 std::forward 完美转发给元素构造函数，直接在容器已分配内存上 placement new 原地构造——全程一次构造，无临时对象、无拷贝/移动。

**性能差异在哪**。`vec.push_back(MyClass("hello", 42))` 实际发生三件事：① 构造临时对象 ② 移动构造进容器内存 ③ 析构临时对象。`vec.emplace_back("hello", 42)` 只有一次构造。构造函数开销大时（涉及内存分配、IO）差距明显。但若你手里已有现成对象 obj：`push_back(obj)` 与 `emplace_back(obj)` 效果完全一样——都是拷贝构造。emplace 的优势只在"从参数直接构造"的场景。

**参数转发灵活性**。push_back 只收一个参数（对象本身）；emplace_back 收任意多个参数，对应元素类型的任意构造函数。如 `map.emplace(key, value)` 直接传 pair 的两个构造参数，不必先构造 std::pair。

#### 高频追问

**Q：emplace_back 总能避免拷贝/移动吗？**
不能。vector 需要扩容（capacity 不够）时所有已有元素都要搬到新内存——这个开销与 push_back/emplace_back 无关。emplace 省的是"新元素入容器"这一步的临时对象开销，不是扩容搬迁开销。

**Q：什么时候 push_back 反而更合适？**
手里已有构造好的对象时，push_back(obj) 语义更清晰。另外 emplace_back 接任意参数可能导致隐式转换不易察觉（如 vec.emplace_back(0) 意外命中单参构造函数），push_back 类型检查更严格。

**Q：emplace_back 的异常安全性？**
构造函数抛异常时，emplace_back 保证容器状态不变（强异常安全）。构造成功后扩容时移动抛异常的行为取决于元素是否有 noexcept 移动构造——与 push_back 相同。

**Q：实际开发怎么选？**
一条原则：从参数直接构造 → emplace_back；已有现成对象 → push_back。性能关键路径优先 emplace_back；普通代码优先可读性，两者皆可。

### 1. 堆与栈

**场景还原**："堆栈有什么区别、C++ 内存怎么分区？"——答"栈自动管、堆手动管"只是第一层。追问"为什么栈快堆慢""栈溢出怎么发生""堆碎片怎么产生"，考的是对进程内存模型的完整认知。

#### 三句话版本

C++ 进程内存从低地址到高地址依次是：**代码段**（.text，只读机器指令）→ **数据段**（.data，已初始化全局/静态变量）→ **BSS 段**（未初始化全局/静态变量，自动清零）→ **堆**（向上生长，程序员手动管理，空间大效率低）→ **栈**（向下生长，编译器自动管理，空间小效率极高）。核心结论：栈是编译器自动打理的高效内存，适合生命周期短、大小固定的局部变量；堆是程序员手动打理的大容量内存，适合生命周期长、大小动态的对象。

#### 六个维度对比

- **管理方式**：栈由编译器自动分配释放（进函数压栈、返回弹栈），程序员零参与；堆经 new/delete 手动管理，忘释放即泄漏。
- **空间大小**：栈很小（Linux 默认 8MB、Windows 默认 1MB），超限即栈溢出；堆很大（32 位系统可达数 GB），几乎不受限。
- **碎片问题**：栈严格后进先出、连续释放，永不产生碎片；堆频繁 new/delete 后中间释放的小块无法满足大块请求，碎片丛生。
- **生长方向**：栈向低地址长，堆向高地址长，两者相向而行，中间是可用空间。
- **分配效率**：栈分配只动栈指针（一条 CPU 指令），极快；堆分配要搜空闲链表、可能触发系统调用扩内存，慢得多。
- **线程安全**：每个线程有独立栈，天然隔离；堆是全体线程共享的，多线程并发 new/delete 需要加锁（这也是堆分配慢的原因之一）。

#### 高频追问

**Q：栈溢出怎么发生？**
栈空间有限（通常几 MB），递归过深（每层调用压一个栈帧）或栈上开超大数组，都会触顶——SIGSEGV，进程被杀。解法：递归改迭代；大数组放堆上（vector 代替原生数组）。

**Q：堆分配为什么比栈慢？**
三个原因叠加：① 要在空闲链表里搜索合适大小的块（O(n)）；② 多线程环境要加锁保护堆数据结构；③ 空闲不足时需经 brk/mmap 系统调用向内核要新页面。栈分配一条指令改栈指针寄存器，O(1) 完成。

**Q：实际项目里怎么管堆内存？**
现代 C++ 原则：能不手动 new/delete 就不手动。智能指针管生命周期、容器代替手动数组、全程遵循 RAII——构造获取、析构释放。性能敏感场景（游戏引擎、高频交易）用内存池预分配一大块，避开频繁系统调用与碎片。

**Q：堆对象和栈对象的行为差异？**
生命周期：栈对象随作用域自动析构，堆对象必须手动 delete。地址稳定性：堆对象地址终身不变（适合被指针引用），栈对象地址函数返回即失效（禁止返回局部变量指针）。拷贝语义：栈对象赋值是值拷贝，堆对象通常靠指针传递避开拷贝开销。

### 2. new 与 malloc

**场景还原**：列举几条差异人人会，追问"new 的底层调用链是什么""placement new 怎么配合 malloc 用""delete[] 为什么不能被 delete 替代"就断片了。核心认知：new 干两件事（分配内存 + 调构造），malloc 只干一件（分配内存）。

#### 三句话版本

new 是 C++ 运算符，一次完成两步：先经 operator new 分配内存，再在内存上调构造函数。malloc 是 C 库函数，只分配指定大小的原始内存，不碰构造。对应地，delete 先析构再释放，free 只释放；new 失败抛 bad_alloc，malloc 失败返回 NULL；new 返回具体类型指针（类型安全），malloc 返回 void* 需强转。

#### 展开讲

**new 的完整链路。** `new MyClass(10)` 被编译器拆成两步：① `operator new(sizeof(MyClass))` 分配内存（默认实现内部调 malloc）；② 在这块地址上调 MyClass 构造函数。完整链条：new → operator new → malloc → mmap/brk（内核层）。对应的 `delete obj` 也是两步：先 `obj->~MyClass()`，再 `operator delete(obj)`（内部通常调 free）。

**malloc 只做一件事。** `malloc(sizeof(MyClass))` 向系统要一块指定大小的原始内存，返回 void*——里面是垃圾值，无任何初始化。你不能直接把它当对象用：成员没初始化、虚表指针没设置，行为未定义。对应的 `free(obj)` 只释放内存，不调析构——对象若持有堆内存（如 string 成员），直接 free 就是泄漏。

**其他关键差异**：new 自动算大小（编译器算 sizeof），malloc 必须手传字节数；new 可被类重载（自定义内存池），malloc 不能重载；new[] 分配数组时额外记录元素个数，delete[] 按记录批量析构，混用 delete 只析构第一个元素，其余全漏。

#### 高频追问

**Q：malloc 之后想当对象用怎么办？**
placement new：`MyClass* obj = new (mem) MyClass(10);`（mem 是 malloc 返回的指针）。它不分配内存、只在指定地址调构造。销毁时手动 `obj->~MyClass()`，再 `free(mem)`。内存池正是这套组合拳。

**Q：new 底层一定调 malloc 吗？**
不一定。operator new 的默认实现通常调 malloc，但可以重载换成自己的分配器（内存池等）。标准只要求 operator new 返回足够大的对齐内存，不规定底层实现。

**Q：什么时候该用 malloc？**
与 C 代码交互（C 没有 new）；分配 POD 的原始内存块（如网络缓冲区 char*）；实现自定义分配器。现代 C++ 绝大多数场景用 new（更好的是用智能指针 + make_shared/make_unique），只有底层系统编程才碰 malloc。

**Q：delete[] 为什么不能换成 delete？**
new[] 分配数组时在块头多存了几字节记录元素个数 N。delete[] 读取 N、循环调 N 次析构、再释放整块。换成 delete 只调一次析构（第一个元素），剩下 N-1 个资源全漏。POD 类型（无析构函数）混用虽不崩，但仍是未定义行为——不要这么干。

### 3. free 与 delete

**场景还原**："free 和 delete 有什么区别、能混用吗？"——答"delete 会调析构"只答了一半。追问"delete 底层到底做几步""混用为什么是未定义行为""delete 和 delete[] 为什么不能互换"才是完整考点。

#### 三句话版本

**free**：C 库函数，配 malloc 使用，只做一件事——把内存还给系统，不碰任何析构。**delete**：C++ 运算符，配 new 使用，做两件事——先调对象析构函数（释放对象内部管理的资源），再释放对象本身占的内存。一句话：free 管内存，delete 管对象（析构 + 内存）。

#### 展开讲

**delete 的底层分解。** `delete p` = 第一步 `p->~T()`（析构） + 第二步 `operator delete(p)`（释放内存），而 operator delete 的默认实现就是 free。所以：delete = 析构 + free。对称地，new = operator new（默认 malloc）+ 构造函数。

**为什么不能混用。** new 出来的对象用 free 释放：析构函数不执行，对象内部管理的资源（堆内存、文件、锁）全部泄漏。malloc 出来的内存用 delete 释放：delete 会试图调析构函数，但这块内存上根本没有正确构造的对象——未定义行为。

**delete 与 delete[] 的分工。** `new T[n]` 会在内存块前部偷偷记录元素个数。delete[] 读取该数字、逐个析构每个元素、再释放整块内存。若用 delete 释放数组：只析构第一个元素，其余全漏；且内存布局不匹配，可能直接崩堆。

**free 的底层行为。** `free(p)` 先找 p 前面的 metadata（malloc 分配时加的头部，记录块大小），标记为已释放，然后尝试与相邻空闲块合并（减碎片）。超大块（通常 > 128KB）直接 munmap 还内核；普通块挂回空闲链表等下次 malloc 复用。

#### 高频追问

**Q：delete nullptr 会怎样？**
完全安全。C++ 标准明确：对 nullptr 调 delete 是合法空操作，所以释放前不必判空。free(NULL) 同样安全——C 标准也有此规定。

**Q：为什么必须区分 delete 和 delete[]？**
数组与单个对象的内存布局不同：new T[n] 在块头额外存元素个数（通常 4/8 字节），delete[] 依赖这个数字决定析构多少个对象。用 delete 释放数组：不知个数、只析构第一个，且释放起始地址可能错位（头部偏移），堆损坏。

**Q：现代 C++ 还需要手写 new/delete 吗？**
尽量不需要。智能指针管堆内存、容器管动态数组；手动 new/delete 容易忘释放（泄漏）或重复释放（崩溃），智能指针靠 RAII 自动管理生命周期，从根源消除这两类事故。

**Q：operator new / operator delete 能重载吗？**
能，全局与类内都行。常见用途：自定义内存池（降 malloc 开销）、泄漏检测（记录每次分配）、对齐分配（满足 SIMD）。注意重载 operator new 只负责分配内存，构造函数由编译器自动调用；operator delete 同理，析构也是编译器自动调。

### 4. placement new

**场景还原**："placement new 是什么、有什么用？"——答"在指定地址构造对象"只是第一层。追问"为什么不能用 delete 释放""内存对齐怎么保证""标准库哪些组件在用它"才是完整答案。

#### 三句话版本

普通 new 两步走：分配内存 + 调构造。placement new 只做第二步——在你给定的地址上调构造函数，**不分配任何内存**。语法 `new (ptr) Type(args)`，ptr 是一块已就绪的内存。销毁时不能用 delete（它会试图释放这块内存，而这内存不是 new 分配的），必须手动 `obj->~Type()`，再按内存的原始来源释放。

#### 展开讲

**与普通 new 的关系。** 普通 `new MyClass(10)` 拆成两步：operator new 分配 + 构造。placement new 跳过第一步、直达构造。底层实现极其简单——标准库有个特殊重载：`void* operator new(size_t, void* ptr) noexcept { return ptr; }`，什么都不做、原样返回你传入的指针。

**为什么不能用 delete 释放。** delete 干两件事：析构 + operator delete 释放内存。但 placement new 构造的对象，内存可能来自栈上 char 数组、内存池、共享内存段——都不归堆分配器管，对它调 operator delete 是未定义行为（通常直接崩）。正确流程：手动调析构 `obj->~MyClass()`，再按来源释放（栈上的自动回收、内存池的还给池、`new char[]` 的用 delete[]）。

**内存对齐要求。** placement new 要求地址满足目标类型的对齐要求（alignof(Type)）。用 char 数组当缓冲区时必须加 `alignas(Type)`，否则某些架构上触发硬件异常或性能大幅下降。C++17 的 std::aligned_storage 或直接 alignas 都能解决。

**标准库里的 placement new**：

- vector 扩容：分配新的大块内存，用 placement new 在新内存上移动构造旧元素
- optional：内部一块 aligned_storage，有值时 placement new 构造、无值时调析构
- variant：在同一块内存上按需构造不同类型的对象
- 一切内存池/对象池的实现基础

#### 高频追问

**Q：为什么不能 memcpy 代替 placement new？**
memcpy 只搬字节、不调构造：有虚函数的类，虚表指针不会被正确设置；持有资源的类（string、vector 成员），内部指针会指向错误地址。只有 POD 类型可以 memcpy，其他类型必须 placement new。

**Q：placement new 会失败吗？**
不会。标准 placement operator new 标了 noexcept，它只返回传入指针、无失败路径。但构造函数本身可能抛异常——若构造抛了，对象未成功构造、无需调析构，但内存仍要按原始方式释放。

**Q：同一块内存能反复构造不同对象吗？**
能，这正是典型用法：先析构旧对象、再 placement new 新对象，variant 切换类型就这么干。注意新对象的大小和对齐要求不能超过这块内存的容量。

**Q：placement new 和内存池什么关系？**
内存池的核心思路"预分配一大块、按需切割"，切割出的块上构造对象靠 placement new、销毁靠手动析构——从而避开频繁 malloc/free 的开销与碎片。游戏引擎、数据库、高频交易系统大量使用这套模式。

### 5. 内存三大问题

**场景还原**：能背定义的人很多，能答"泄漏为什么不会立刻崩""野指针为什么有时不报错""越界和堆溢出什么关系"的不多。三者的病根一句话区分：泄漏是"忘了还"，野指针是"用了废的"，越界是"写出界了"。

#### 三句话版本

**内存泄漏**：堆上申请了内存却丢失了指针，这块内存从此无人认领。**野指针**：指针还在，指向的内存已被释放或失效，再次访问即非法。**内存越界**：访问了数组或动态内存合法范围之外的位置，可能覆盖其他数据。三者共同点：都可能崩溃或造成安全漏洞；区别在发生机制与表现形式。

#### 展开讲

**内存泄漏**。new/malloc 申请后，指针被覆盖、函数返回、异常跳出——地址丢了，永远无法释放。短期不崩，长期运行（服务器、嵌入式）内存被慢慢吃光，最终分配失败或被系统 OOM 击杀。**防治**：C++ 里最有效的武器是 RAII——智能指针管堆内存，离开作用域自动释放；手动管理时保证每条路径（含异常路径）都有 delete/free。

**野指针**。指针本体还在，指向的内存已被 delete/free。经它读写是未定义行为：可能读到旧数据（看起来"正常"）、读到垃圾值、也可能 SIGSEGV。最危险的是"看起来正常"——bug 潜伏很久才爆发。**防治**：delete 后立刻置 nullptr；不返回局部变量地址；用智能指针替换裸指针（析构后自动失效）。

**内存越界**。下标超出 [0, size-1]，或往 malloc(10) 的 10 字节之外写。越界写入可能覆盖相邻变量、堆管理元数据、甚至函数返回地址——缓冲区溢出攻击的根源。**防治**：用 vector 等容器替代裸数组（debug 模式带边界检查）；编译加 -fsanitize=address；循环里严格校验下标。

#### 高频追问

**Q：智能指针能完全杜绝泄漏吗？**
不能一劳永逸：shared_ptr 循环引用会让计数永不归零、内存永不释放，解法是 weak_ptr 打断引用环。智能指针也不管非内存资源（文件句柄、socket）——那些要自定义 deleter 或 RAII 封装类。

**Q：free/delete 之后，为什么野指针有时"还能用"？**
free/delete 只是声明"这块内存可回收"，并不会立刻清零或归还操作系统。短期内数据仍在原地，野指针读到的可能是旧值——这恰恰最危险：bug 不立刻暴露，等内存被重新分配给别人，事故才爆。

**Q：越界和堆溢出什么关系？**
堆溢出是越界的子集——往堆缓冲区外写；栈上数组越界叫栈缓冲区溢出。两者都是越界写入，攻击面不同：栈溢出可覆盖返回地址劫持控制流，堆溢出可覆盖堆元数据或相邻对象的 vtable。

**Q：泄漏为什么不会立刻崩？**
泄漏只是"内存没还"，程序逻辑本身没错。虚拟内存机制允许进程持续申请，直到地址空间或物理内存耗尽。长期运行的服务（Web 服务器）对此最敏感，可能跑几天才 OOM。

### 6. 碎片与溢出

**场景还原**："什么是内存碎片""栈溢出和堆溢出差在哪"——背定义不难，追问"外部碎片为什么比内部碎片难治""堆溢出为什么是安全问题"才见功底。

#### 三句话版本

**内存碎片**：空闲内存总量够用，但因不连续（外部碎片）或分配粒度浪费（内部碎片）而无法满足请求。**栈溢出**：栈空间被耗尽——如无限递归把栈帧堆满。**堆溢出**：往动态分配的内存块之外写数据——本质是越界访问，常被利用做攻击。一句话对比：一个是"装不下了"，一个是"写出界了"。

#### 展开讲

**内存碎片两类**：

- **外部碎片**：频繁分配释放不同大小的块后，空闲内存被切成许多不连续小块——单块不够大，总量却够。这就是"有钱但花不出去"。C/C++ 里尤其难治：指针直接指向地址，无法像 Java 那样做内存压缩（移动对象必须更新所有指针）。
- **内部碎片**：分配器按固定粒度分配（如 8 字节对齐），要 5 字节给 8 字节，多的 3 字节浪费。内存池同样有此问题——池块大小固定，小请求浪费空间。

**栈溢出 vs 堆溢出**

| 维度 | 栈溢出 (Stack Overflow) | 堆溢出 (Heap Overflow) |
| --- | --- | --- |
| 发生区域 | 栈内存（向低地址增长） | 堆内存（动态分配区） |
| 根本原因 | 空间耗尽：递归过深或栈上变量过大 | 越界写入：往 malloc/new 分配的块外写 |
| 触发方式 | 通常是编程失误（无限递归、栈上大数组） | 可以是无意错误，也常是攻击手段 |
| 后果 | 立即崩溃（SIGSEGV），行为确定 | 可能立刻崩，也可能潜伏——覆盖了什么决定后果 |
| 安全影响 | 影响可用性（程序挂了） | 影响安全性（可能被利用执行任意代码） |

#### 高频追问

**Q：外部碎片为什么比内部碎片难治？**
内部碎片是"已知的浪费"，上限可控——选合适的分配粒度或池块大小即可。外部碎片是"全局的混乱"，取决于分配释放的随机序列，无法预测。理论上可做内存压缩（移动已分配块合并空闲区），但 C/C++ 指针是裸地址，移动对象必须更新所有指向它的指针——几乎不可能。只能靠分配策略（best-fit、buddy system）缓解。

**Q：堆溢出为什么是严重的安全问题？**
堆溢出可覆盖堆中相邻数据：精心构造的内容能覆盖函数指针让它指向恶意代码、覆盖对象 vtable 控制执行流、改写相邻数据改变逻辑。配合 ROP 链，即便开了 DEP/NX 也能执行任意代码。

**Q：怎么避免栈溢出？**
递归改迭代；不在栈上放大数组（改堆分配）；给递归设深度上限；编译加 -fstack-protector 检测。

**Q：所有递归都会栈溢出吗？**
不会，深度在栈容量内就没事。遍历深度 1000 的二叉树没问题（栈深 ≈ 树高），但递归遍历百万节点链表必溢（栈深 ≈ 节点数）。尾递归可被编译器优化成循环，不增长栈。

### 7. 避免内存碎片

**场景还原**："项目里怎么处理内存碎片？"——答"用内存池"只算入门。这题考的是从哪些层面**系统性**地压制碎片，而不是背一个名词。

#### 三句话版本

避免碎片的核心策略：**减少不同生命周期、不同大小的内存块交替申请与释放**。主要手段：内存池处理小对象高频分配；STL 容器（如 vector）预分配连续内存；智能指针防止泄漏造成的不可回收碎片。

#### 展开讲

先分清两种碎片：

- **外部碎片**：空闲总量够用，但分散在不连续小块中，满足不了大请求
- **内部碎片**：分配的块比实际请求大，多出部分被浪费

避免策略按层次递进：

**1. 能不动态分配就不分配。** 优先栈内存、静态存储期对象或成员变量——栈分配快且天然无碎片。

**2. 用 STL 容器管理连续内存。** vector、string、array 内部管理一块连续的动态增长内存，元素内存连续，大幅减少外部碎片；提前知道规模就 reserve() 预分配，避免多次扩容制造碎片。

**3. 智能指针防泄漏。** unique_ptr、shared_ptr 走 RAII 自动管理生命周期，杜绝"忘释放导致的永久碎片"。作用是间接的，但很关键。

**4. 对象池（Object Pool）。** 高频申请释放固定大小的小对象（链表节点、网络包）时的终极方案：一次性分配一大块内存，内部维护空闲链表，分配与归还都是 O(1)，完全规避外部碎片。

**5. 自定义分配器（Custom Allocator）。** STL 容器支持注入自定义分配器，可实现基于内存池的分配策略替换默认 new/delete，为特定类型提供无碎片分配。

递进总结：从"能不分配就不分配"，到"分配了就连续分配"，再到"自己管理分配"——层次感是这题的得分点。

#### 高频追问

**Q：外部碎片和内部碎片各举个例子？**
外部碎片：堆上零散分布着 A、B、C 三个对象，中间有空隙，空闲总量够放 D 但没有一块连续空间装得下。内部碎片：malloc 为对齐多给几字节，或池块大小固定而你请求的对象比块小。

**Q：list 和 vector 在碎片上有什么差别？**
vector 单块连续内存、无外部碎片，扩容时产生暂时碎片；list 每个节点独立分配，频繁插删产生大量外部碎片——高频场景慎用 list。

**Q：智能指针怎么帮助减少碎片？**
贡献在防泄漏：泄漏的内存对系统而言就是永远无法使用的碎片。智能指针确保内存被正确释放，间接对抗泄漏型碎片。

**Q：线程安全的对象池怎么设计？**
最简单：mutex 保护空闲链表。高性能：线程本地存储（TLS），每线程独立空闲列表、零锁竞争；本线程池耗尽时再访问全局加锁的共享池。

### 1. C++11 新特性

**场景还原**："C++11 有哪些新特性、最核心的改进是什么？"——罗列十几个特性名只值零分。面试官想听的是特性之间的关系、为什么引入、解决了什么问题。抓手的做法：从三个设计目标出发，把零散特性串成体系。

#### 三句话版本

C++11 是现代 C++ 的分水岭，所有新特性围绕三大目标展开：

- **性能优化**：右值引用、移动语义、constexpr——砍掉多余拷贝，编译期能算的提前算
- **安全提升**：智能指针、nullptr、enum class、static_assert——从语言层堵住经典坑
- **表达力**：auto、Lambda、范围 for、初始化列表、变参模板——更简洁、意图更明确

#### 展开讲

**性能线：右值引用与移动语义。** C++11 之前，函数返回大对象、容器插入临时对象都要深拷贝。右值引用（T&&）让编译器识别"即将销毁的临时对象"，直接偷走资源而非复制；配合 std::move 显式触发移动。constexpr 则是另一方向——把编译期可算的值提前算好，运行期零开销。

**安全线：智能指针与类型安全。** unique_ptr / shared_ptr / weak_ptr 用 RAII 管堆内存，根治忘 delete、重复 delete、悬空指针三大顽疾。nullptr 取代类型不安全的 NULL（本质是整数 0）。enum class 解决传统枚举的命名污染与隐式转换。static_assert 把错误拦在编译期。

**表达力线：auto 与 Lambda。** auto 让编译器推类型，告别冗长的迭代器类型；decltype 取表达式精确类型，模板编程主力。Lambda 让"就地定义小函数"成为可能，配 STL 算法极顺手；范围 for 简化遍历；`{}` 初始化列表统一各处初始化语法；变参模板让泛型代码处理任意数量的参数。

**并发线：标准线程库。** C++11 之前多线程只能靠平台 API（pthread、Windows API）；C++11 提供 std::thread、std::mutex、std::condition_variable、std::atomic，并发代码从此跨平台。

#### 高频追问

**Q：auto 和 decltype 的区别？**
auto 用于变量声明、按初始化式推导、忽略顶层 const 和引用；decltype 取表达式精确类型、保留 const 与引用。日常代码用 auto 简化，模板返回值推导等需要精确类型的场合用 decltype。

**Q：右值引用为什么能提速？**
它让编译器区分"还要继续用的对象"和"马上销毁的临时对象"。对临时对象，移动构造直接接管内部资源（把 vector 的内部指针偷过来），不再分配新内存逐元素拷贝——代价从 O(n) 降到 O(1)。

**Q：三种智能指针怎么选？**
独占所有权 → unique_ptr（零开销，默认之选）；共享所有权 → shared_ptr（有计数开销）；weak_ptr 配合 shared_ptr 打破循环引用——观察但不拥有。

**Q：Lambda 捕获列表有什么讲究？**
[=] 全值捕获、[&] 全引用捕获：值捕获安全但拷贝有开销；引用捕获零开销但悬垂风险——Lambda 比被捕获变量活得久时引用就空了。实践建议显式列出要捕获的变量，意图更清晰。

### 2. C++11 多线程

**场景还原**："C++11 多线程和锁了解吗？lock_guard 和 unique_lock 有什么区别？"——知道 mutex 和 lock_guard 只是起点，unique_lock 为什么能配合条件变量、死锁怎么防，才是分水岭。

#### 三句话版本

C++11 用四个头文件搭起完整线程栈：`<thread>`（std::thread 建线程）、`<mutex>`（互斥锁 + RAII 锁管理器 lock_guard/unique_lock）、`<condition_variable>`（等待-通知）、`<atomic>`（无锁原子操作）。

#### 展开讲

**线程管理。** std::thread 接受任意可调用对象（函数指针、lambda、仿函数）作线程入口。创建后必须 join()（等结束）或 detach()（分离），两者都不调——析构时直接 std::terminate。

**互斥锁全家桶**：

- std::mutex：基本互斥锁，不可重入
- std::recursive_mutex：同一线程可多次加锁（递归场景）
- std::timed_mutex：支持超时，try_lock_for() 避免永久阻塞

**RAII 锁管理**。直接 lock()/unlock() 容易忘解锁或异常路径泄漏。RAII 包装器解决：lock_guard 构造加锁、析构解锁、中途不可操作——简单轻量，够用就用它；unique_lock 更灵活——延迟加锁、手动 lock/unlock、转移所有权，条件变量必须用它（wait() 需要中途放锁）。

**条件变量**。condition_variable 实现"等条件满足再继续"的生产者-消费者模式：wait() 原子地放锁并挂起线程，被 notify_one()/notify_all() 唤醒后重新加锁继续。

**原子操作**。std::atomic<T> 对简单类型（int、bool、指针）提供无锁原子读写，比 mutex 开销小得多；适合计数器、标志位等简单同步，复杂逻辑仍需锁。

#### 高频追问

**Q：lock_guard 和 unique_lock 怎么选？**
lock_guard 更轻：构造即锁、析构即解，中途不可动。unique_lock 更强：延迟加锁（std::defer_lock）、手动 lock/unlock、配合条件变量。日常临界区用 lock_guard；需要条件变量或中途放锁才上 unique_lock。

**Q：什么是死锁，怎么避免？**
两线程各持一把锁、又都在等对方的锁——永久阻塞。四条防线：统一加锁顺序（所有线程都先 A 后 B）；std::lock() 一次锁多个 mutex；RAII 保证异常时也解锁；timed_mutex 超时兜底。

**Q：条件变量为什么必须配 unique_lock？**
wait() 内部干两件事：放锁（让别人能改条件）+ 重新加锁（唤醒后继续操作共享数据）。lock_guard 不支持中途放锁，只有 unique_lock 做得到。

**Q：atomic 和 mutex 怎么选？**
单变量的简单读写（计数器、标志位）用 atomic，零锁开销；多变量复合操作（同时改 balance 和 log）必须 mutex——atomic 只保证单个操作的原子性，不保证多个操作之间的一致性。

### 3. 左右值引用

**场景还原**："一个绑左值一个绑右值"只是入门答案。追问"右值引用解决了什么问题""std::move 到底干了什么"，暴露的是对资源转移思想的理解深度。

#### 三句话版本

**左值引用 T&** 绑定有名字、有地址的持久对象，用来避免拷贝；**右值引用 T&&** 绑定临时对象或将亡值，让编译器把资源"偷"过来而非深拷贝——这就是移动语义。std::move 本身不移动任何东西，它只把左值强转成右值引用，宣告"这个对象我不要了，你可以搬走"。

#### 展开讲

**绑定规则**。左值引用只能绑左值——有名字、可取地址的对象（变量、数组元素）。右值引用只能绑右值——临时对象 string("hello")、字面量 42、函数返回的临时值。特例：const T& 也能绑右值，这是 C++11 之前接住临时对象的唯一方式，但只读，偷不了资源。

**为什么需要右值引用**。`vector<string> v; v.push_back(getString());` 在 C++11 之前会把 getString() 返回的临时 string 深拷贝一份再入容器，临时对象随后销毁——它马上就要死了，堆内存完全可以接管，深拷贝纯属浪费。右值引用就是让编译器识别"这个对象即将销毁"，从而触发移动构造而非拷贝构造。

**std::move 的本质**。`std::move(x)` ≈ `static_cast<T&&>(x)`：不动任何数据，只把 x 的类型从左值转成右值引用。真正的资源转移发生在移动构造函数里——拿走源对象指针、把源指针置空。move 之后源对象处于"有效但未指定"状态，不能再假设其值。

#### 高频追问

**Q：引用折叠规则是什么？**
模板或 typedef 中出现"引用的引用"时折叠：只有 `T&& &&` 折叠成 `T&&`，其余三种（T& &、T& &&、T&& &）全折叠成 `T&`。口诀：见左值引用即折叠为左值引用。

**Q：万能引用和右值引用怎么区分？**
写法相同（T&&），看上下文：出现在模板类型推导上下文（`template<typename T> void f(T&& arg)` 或 `auto&& x`）的是万能引用；T 是具体类型（如 string&&）则是普通右值引用。万能引用配合 std::forward 实现完美转发。

**Q：移动构造为什么必须 noexcept？**
vector 扩容搬元素时，若移动构造可能抛异常，搬一半抛出后已搬走的元素回不去——数据损坏。标准库看到移动构造未标 noexcept 就退回拷贝构造保异常安全。标了 noexcept 才能吃到移动的性能红利。

**Q：move 之后的对象还能用吗？**
能用，但不能假设其值。标准保证"有效但未指定"：可以赋新值、可以析构，但读出来的内容没有意义。

### 4. 移动语义

**场景还原**："移动语义的作用和原理？"——答"避免深拷贝"只值两成。追问"std::move 做了什么""move 后对象还能用吗""编译器什么时候自动移动"才是完整考点。核心一句话：移动语义把 O(n) 深拷贝变成 O(1) 指针接管。

#### 三句话版本

移动语义让对象"搬家"而非"克隆"。C++11 之前传/返一个 vector<string> 必须深拷贝所有元素——分配新内存、逐个复制、释放旧内存，O(n)。移动语义经右值引用 T&& 识别"对象马上要死了"，移动构造直接拿走源对象内部指针、置空源指针，全程只是两次指针赋值——O(1)。

#### 展开讲

**它解决的问题**。临时对象（函数返回值、表达式中间结果）赋给新变量时必须走拷贝构造：分配内存、逐字节复制、释放临时对象。对管理堆内存的类（string、vector、自定义资源类），这纯属浪费——临时对象马上析构，内存完全可以接管。移动语义就是让编译器识别"源对象即将销毁"并触发移动构造。

**实现原理**。右值引用 T&& 是语法基础：只绑右值，编译器看到参数类型 T&& 就知道可以偷资源。移动构造的实现极简：拿走源对象指针 + 源指针置 nullptr，不分配内存、不复制数据。移动赋值类似，多一步"先释放自己的旧资源"。

**std::move 的本质**。`std::move(x)` ≈ `static_cast<T&&>(x)`：不移动任何数据，只把左值强转成右值引用，宣告"这个对象我不要了，你可以搬走"。真正的转移发生在移动构造里。

**移动后的源对象状态**。标准要求"有效但未指定"：可析构、可赋新值，但不能假设还有原来的数据。典型实现是置 nullptr——这样析构时 delete nullptr 是安全的。

**编译器自动触发移动的场景**：函数返回局部对象（RVO/NRVO 失败时）；vector 扩容搬元素（移动构造标了 noexcept 才生效）；用临时对象初始化新对象；push_back(临时对象)。

#### 高频追问

**Q：移动构造为什么要 noexcept？**
vector 扩容搬元素时若移动抛异常，已搬走的元素回不去——数据损坏。标准库见移动构造未标 noexcept 就退回拷贝构造保异常安全。标了 noexcept 才能享受移动提速。

**Q：什么时候该给类实现移动语义？**
类管理外部资源（堆内存、文件句柄、socket、锁）且拷贝代价高时。类只有几个 int 成员的话移动与拷贝没差别，不用专门写。unique_ptr 是典型——禁止拷贝、只许移动，因为所有权必须唯一。

**Q：std::move 之后源对象还能用吗？**
能用，但不能假设值。标准保证"有效但未指定"：可赋新值、可析构，不能当有意义数据读。工程实践：move 之后尽量别碰源对象，除非给它赋新值。

**Q：移动语义和 RVO 什么关系？**
RVO 是编译器优化，直接在目标位置构造对象、连移动都省——零开销。移动语义是 RVO 失败时的兜底。C++17 强制部分场景 RVO，但多 return 路径时 RVO 可能失败，此时移动语义顶上。

### 5. 完美转发

**场景还原**："什么是完美转发、怎么实现？"——答"用 std::forward"只是名词。追问"forward 和 move 差在哪""引用折叠怎么折叠""什么时候转发会失败"才是完整链路。

#### 三句话版本

完美转发 = 在函数模板里把参数**按原始值类别**（左值/右值）无损传给下一层。三个机制协作：万能引用 T&& 接收参数（左值右值通吃）、引用折叠规则推导出正确的引用类型、std::forward<T>(arg) 按推导结果有条件恢复右值属性。效果：进来是左值转发左值，进来是右值转发右值，移动语义不丢失。

#### 展开讲

**它解决什么问题**。C++11 之前模板转发参数有个致命缺陷：无论传进来的是左值还是右值，进了函数体都变左值（有名字的变量都是左值）。调用者传的是临时对象（右值），转发给目标函数却走拷贝而非移动——性能白丢。例如工厂函数 `template<typename T, typename Arg> T* create(Arg arg) { return new T(arg); }`，即便传右值 `create<string>(string("hello"))`，arg 在函数体内是左值，走的是拷贝构造。

**万能引用 + 引用折叠**。万能引用 T&&（在模板类型推导上下文中）左值右值通吃。关键在折叠规则：传左值时 T 推导为 X&，T&& 折叠成 X&（左值引用）；传右值时 T 推导为 X，T&& 就是 X&&（右值引用）。口诀：有左值引用参与就折叠成左值引用（& + && = &），只有 && + && 才是 &&。

**std::forward 怎么工作**。`std::forward<T>(arg)` 做"有条件转右值"：T 被推导为左值引用（原始参数是左值）→ 什么都不做，arg 保持左值；T 被推导为非引用（原始参数是右值）→ 等价 `static_cast<T&&>(arg)`，把 arg 转回右值。"完美"的含义就在这——原来是什么，转发出去还是什么。

**forward 与 move 的分工**。move 无条件转右值：进出都是右值引用；forward 有条件转右值：按 T 的推导结果决定转不转。move 用在"确定不再需要这个对象"；forward 用在"保持参数原样往下传"。

#### 高频追问

**Q：完美转发最典型的应用？**
工厂函数（make_unique/make_shared 的实现）、容器的 emplace 系列（emplace_back 把参数完美转发给元素构造函数）、回调包装器。共同点：中间层不知道目标函数要左值还是右值，只能原样转发。

**Q：怎么和可变参数模板配合？**
参数包展开：`template<typename... Args> void wrapper(Args&&... args) { target(std::forward<Args>(args)...); }`。每个参数独立推导、独立转发。emplace_back 就是这么实现的。

**Q：完美转发什么时候失效？**
三种情况：传花括号初始化列表 {1,2,3}（模板推不出 initializer_list）；传 0 或 NULL 当空指针（被推成 int 而非指针，应用 nullptr）；传重载函数名或模板函数名（编译器不知选哪个版本来推导）。

**Q：不用 forward 直接传 arg 会怎样？**
arg 在函数体内是左值（有名字），直接传永远走左值版本——移动语义全丢。这就是"不完美转发"：所有参数退化成左值。

### 6. move 与 forward

**场景还原**："move 和 forward 有什么区别？"——答"一个移动一个转发"等于没答。真正的得分点是"无条件 vs 有条件"，外加各自的底层机制与使用边界。

#### 三句话版本

**std::move 是无条件转换**：不管进来的是左值还是右值，一律转成右值引用，语义"我不要了，你拿走"。**std::forward 是有条件转换**：原始参数是右值才转右值引用，左值保持左值，语义"你给我什么，我原样传下去"。两者本质都是 static_cast——不生成任何代码，纯编译期类型操作。

#### 展开讲

**std::move 的机制**。实现一行：`static_cast<remove_reference_t<T>&&>(t)`。无论 T 是什么，先剥引用再加 &&，结果必为右值引用。它不"移动"任何东西，只告诉编译器"此对象可被移动"，真正的移动在移动构造/移动赋值里。使用后源对象进入"有效但未指定"（moved-from）状态：只能析构或重新赋值，不能假设还有原值。

**std::forward 的机制**。靠两条规则配合：万能引用（模板中的 T&&）+ 引用折叠。传左值时 T 推导为 X&，X& && 折叠为 X&，forward 返回左值引用；传右值时 T 推导为 X，X&& 即右值引用，forward 返回右值引用。因此 forward 只在模板函数中有意义——非模板函数没有参数推导，也就没有"保持原始值类别"可言。

#### 核心对比

| 维度 | std::move | std::forward |
| --- | --- | --- |
| 转换方式 | 无条件转右值引用 | 有条件，保持原始值类别 |
| 使用场景 | 明确转移所有权 | 模板中转发参数 |
| 依赖条件 | 无 | 万能引用 + 引用折叠 |
| 本质 | static_cast 剥引用加 && | static_cast 配合推导结果 |

#### 高频追问

**Q：对 const 对象 move 会怎样？**
move 本身不报错，但移动构造/赋值接收的是非 const 右值引用（T&&），const 右值引用匹配不上，退化成拷贝——对 const 对象 move 等于白 move，性能零提升。

**Q：forward 为什么只能用在模板里？**
它的"有条件"依赖模板参数推导结果。非模板函数参数类型写死、无推导过程，也就没有"原始值类别"可保持。

**Q：move 之后还能用源对象吗？**
标准说 moved-from 对象"有效但未指定"：实践只能析构或重新赋值，不能假设还有原资源。标准库容器 move 后通常变空容器，但这不是标准保证。

**Q：什么时候用 move，什么时候用 forward？**
规则一句话：明确不再需要这个对象 → move；模板里收参数要传给下一层 → forward。不能混用——转发场景用 move 会把左值也强转成右值，破坏调用者预期。

### 7. Lambda 表达式

**场景还原**："Lambda 的本质是什么？捕获列表底层怎么实现？"——会写语法只是开始。追问"编译器怎么转换""mutable 为什么存在""无捕获 lambda 为什么能转函数指针"，考的是对编译器转换原理的理解。

#### 三句话版本

Lambda 本质是编译器生成的**匿名仿函数类**。`[捕获列表](参数){ 函数体 }` 会被转换成一个结构体：捕获变量成为成员变量，函数体成为 operator() 的实现。值捕获 [x] → x 成结构体成员（拷贝一份）；引用捕获 [&x] → x 成引用成员；无捕获 [] → 结构体无成员，等价普通函数，所以能隐式转函数指针。

#### 展开讲

**编译器转换过程**。`[threshold](int x) { return x > threshold; }` 实际生成：

```cpp
struct __lambda_1 {
    int threshold;  // 值捕获 → 成员变量
    bool operator()(int x) const { return x > threshold; }
};
```

再用当前作用域的 threshold 初始化这个结构体。所以 lambda 就是一个带 operator() 的对象——与手写仿函数完全等价。

**捕获列表的底层含义**：

- [x] 值捕获：x 拷贝进 lambda 对象，外部 x 的后续变化不影响副本
- [&x] 引用捕获：lambda 持有 x 的引用，经它修改会作用到外部 x
- [=] 全值捕获：用到的外部变量各拷贝一份
- [&] 全引用捕获：用到的外部变量全部按引用
- [x, &y] 混合捕获：x 按值、y 按引用

**mutable 的作用**。默认 lambda 的 operator() 是 const 的——值捕获的变量不能修改（const 成员函数里不能改成员）。加 mutable 去掉 const 限定，允许改值捕获的副本（外部原变量不受影响）。

**无捕获 lambda 与函数指针**。无捕获的 lambda 没有成员变量，等价普通函数，标准允许隐式转换为对应签名的函数指针——可以直接喂给 C 风格回调接口。有捕获的 lambda 转不了：它有状态（成员变量），需要对象承载。

#### 高频追问

**Q：lambda 和函数指针的区别？**
lambda 是对象（编译器生成类的实例），函数指针是纯地址。lambda 可捕获外部变量（有状态），指针不能。lambda 能被内联优化（类型唯一、编译器知道调用目标），函数指针是间接调用、通常不能内联。无捕获 lambda 可退化为指针，有捕获的不行。

**Q：值捕获和引用捕获怎么选？**
值捕获安全但有拷贝开销——lambda 比被捕获变量活得久也没事（是副本）；引用捕获零开销但有悬垂风险——lambda 比变量活得久（异步回调）引用就空了。原则：短生命周期 lambda（同步使用、不出作用域）用引用；长生命周期 lambda（存起来以后用、传异步任务）用值。

**Q：C++14/17/20 对 lambda 的增强？**
C++14：泛型 lambda（参数 auto）、初始化捕获（[x = std::move(obj)] 移动捕获）。C++17：constexpr lambda。C++20：模板 lambda（[]<typename T>(T x)）、可出现在未求值上下文。每代都在把 lambda 推向"万能可调用对象"。

**Q：lambda 什么时候不该用？**
三种情况：函数体超过 5~10 行（可读性差，提取为命名函数）；同一逻辑多处复用（定义普通函数或仿函数）；需要递归（lambda 不能直接递归调用自己，得用 std::function 包装，带性能开销）。

### 8. 仿函数与 Lambda

**场景还原**："仿函数和 lambda 哪个快？"——正确答案是"基本一样"，但只说这一句面试官必然追问"为什么一样""什么时候有差异"。要害在于理解 lambda 的编译器转换：它就是匿名仿函数类。

#### 三句话版本

性能基本持平。编译器把 lambda 转换成匿名仿函数类——带 operator() 的结构体，捕获变量变成结构体成员。编译器视角下两者无本质区别，都能被内联。-O2/-O3 下性能差异通常小于 1%，可忽略。

#### 展开讲

**lambda 的编译器转换**。`[x](int a) { return a * x; }` 实际生成：

```cpp
struct __anonymous {
    int x;
    int operator()(int a) const { return a * x; }
};
```

再用捕获的 x 初始化结构体。lambda 与仿函数底层同源，编译器施加的优化（内联、常量传播）完全一致。

**真正影响性能的因素**不是"用 lambda 还是仿函数"，而是：

- **捕获方式**：值捕获把对象拷进 lambda（大对象开销不可忽略）；引用捕获零开销但有悬垂风险
- **是否经 std::function 包装**：std::function 是类型擦除容器，引入虚调用或堆分配、阻断内联——这才是真正的性能杀手
- **模板 vs 类型擦除**：STL 算法收模板参数，lambda/仿函数都能内联；改走 std::function 就丧失内联机会

**仿函数仍有优势的场景**：

- 多个编译单元间共享同一个可调用对象
- 需要命名（lambda 匿名，调试时看不到名字）
- 需要继承或多态行为
- 需要显式控制特殊成员函数（拷贝、移动）

#### 高频追问

**Q：捕获方式对性能的影响？**
值捕获（[x]）：变量拷贝进 lambda——int 等小类型零开销，string/vector 拷贝代价大。引用捕获（[&x]）：只存引用、零拷贝，但 lambda 比变量活得久时引用悬空。C++14 的移动捕获（[x = std::move(obj)]）可避免拷贝大对象。

**Q：std::function 为什么慢？**
它是类型擦除的通用可调用容器：内部靠虚函数或函数指针做多态调用，编译器无法内联；lambda 捕获数据超过一定大小（通常 16~32 字节）时还会堆分配。性能敏感的热路径别用 std::function 传 lambda——直接用模板参数接收。

**Q：lambda 能完全替代仿函数吗？**
日常 99% 能：lambda 更简洁、就地定义、无需命名。但跨编译单元复用、继承体系、精细控制对象语义时仿函数仍有价值。选择标准是可读性与维护性，不是性能。

**Q：函数指针和 lambda 的区别？**
无捕获 lambda 可隐式转函数指针（无状态、等价普通函数）；有捕获的转不了——有状态需要对象承载。这也是 C 风格回调接口常带一个 void* userdata 传上下文的原因。

### 9. RAII 机制

**场景还原**："介绍一下 RAII"——答"构造获取、析构释放"只是起点。追问"为什么析构一定会被调""构造函数抛异常怎么办""和智能指针什么关系"，考的是对这套设计哲学成立前提的把握。

#### 三句话版本

RAII 的核心思想：**资源生命周期绑定对象生命周期**——构造函数获取资源，析构函数释放资源。C++ 保证栈对象离开作用域时析构必被调用（异常也不例外），资源因此不可能泄漏。unique_ptr、shared_ptr、lock_guard 都是标准库中的 RAII 实现。

#### 展开讲

**RAII 为什么能保证不泄漏**。关键在 C++ 的**确定性析构**：栈对象离开作用域时编译器保证调析构——正常返回与异常栈展开（stack unwinding）都算。对比 Java/Go 的 GC：GC 只管内存、不管文件句柄/锁/连接等非内存资源，且回收时机不确定，无法做到"出作用域立即释放"。RAII 把"何时释放"的决策从程序员手里拿走，交给编译器与作用域规则。

**与手动管理的对比**。手动管理（new/delete、fopen/fclose、lock/unlock）的风险：获取与释放之间任何提前 return、异常抛出、分支遗漏都导致泄漏。RAII 把释放逻辑封进析构函数——只要对象在栈上，无论中间发生什么，析构必执行。

**标准库的 RAII 实践**：

- unique_ptr 独占堆内存，出作用域自动 delete
- shared_ptr 引用计数管共享所有权，最后一个析构时释放
- lock_guard/unique_lock 构造加锁、析构解锁，异常也不会忘解锁
- fstream 析构自动关文件

**RAII 类的设计要点**：独占资源（文件、锁）→ 禁拷贝（= delete）+ 允许移动（转移所有权）；共享资源 → 引用计数；析构函数不抛异常——释放失败只能记日志，往外抛会在栈展开时 terminate。

#### 高频追问

**Q：构造函数抛异常，RAII 还成立吗？**
构造函数抛异常 → 对象未构造完成 → 析构不会被调。但 C++ 保证：**已构造完成的成员变量会被正确析构**。所以 RAII 类构造里先取资源 A 再取资源 B，取 B 抛异常时 A 不泄漏——前提是 A 本身也是 RAII 管理（如 unique_ptr 成员）。这正是"RAII 套 RAII"设计的由来。

**Q：RAII 类怎么处理拷贝？**
看资源语义：独占资源（文件、锁）→ 禁拷贝、允许移动；共享资源 → 引用计数（shared_ptr 模式）；值语义资源（字符串、容器）→ 深拷贝。选错会 double free 或泄漏。

**Q：堆上的 RAII 对象能保证释放吗？**
不能。new 出来的对象没人 delete，析构不会被调。RAII 的正确用法：对象放栈上，或用智能指针管堆对象——智能指针本身在栈上，它的析构会 delete 堆对象。裸 new 是 RAII 的天敌。

**Q：RAII 与 Go defer、Python with 的区别？**
defer/with 是语法糖，需要程序员显式写释放逻辑；RAII 是隐式的——类设计正确后，使用者完全不用关心释放。且 RAII 支持所有权转移（移动语义），defer/with 做不到。

### 10. 异常处理

**场景还原**："异常机制了解吗？栈展开是怎么回事？异常和错误码怎么选？"——会用 try-catch 只是起点。栈展开的具体过程、为什么必须按引用捕获、析构为什么不能抛异常，才是完整答案。

#### 三句话版本

C++ 异常基于 try-throw-catch 三件套：try 定义监控范围，throw 抛出异常对象并立即终止当前函数，catch 按类型匹配处理。核心机制是**栈展开（Stack Unwinding）**：从抛出点沿调用链逐层退出，途中自动调用所有局部对象析构——配合 RAII，异常发生时资源也不泄漏。

#### 展开讲

**异常执行流程**。throw 执行后程序不走常规路径，立即开始栈展开：从当前函数退出、沿调用链逐层上溯，直到找到类型匹配的 catch。每退一层，该层所有局部对象的析构自动执行。精髓在于**错误处理与资源清理解耦**：不必每层手动查错误码、手动释放——RAII 对象的析构自动搞定。

**捕获规则**。catch 按声明顺序匹配，命中第一个类型兼容的块。所以派生类异常的 catch 必须写在基类前面，否则永远匹配不到。`catch(...)` 兜一切，通常放最后。

**noexcept 的作用**。C++11 引入，声明"此函数保证不抛"。编译器据此优化——典型例子：STL 容器扩容时若移动构造 noexcept 则用移动而非拷贝。noexcept 函数真抛了异常：直接 std::terminate，不走栈展开。

**异常安全三级**：

- 基本保证：异常后对象处于合法状态，资源不泄漏
- 强保证：异常后状态回滚到操作前（要么成功、要么没变）
- 不抛保证：函数保证不抛（noexcept 标记）

#### 高频追问

**Q：异常和错误码怎么选？**
错误码适合高频、可预期的错误（文件不存在、网络超时）——开销小但易被忽略；异常适合低频、不可恢复的错误（内存耗尽、前置条件被违反）——不会被忽略但有开销。工程实践常混用：底层库用错误码，上层业务用异常。构造函数只能靠异常报错——没有别的选择。

**Q：为什么必须按引用捕获？**
按值捕获发生**对象切片**：抛的是派生类异常、按基类值捕获，派生类信息丢失、多态失效。按引用捕获保多态、还省拷贝。用 const 引用更好——通常不需要改异常对象。

**Q：析构函数为什么不能抛异常？**
栈展开过程中会调局部对象析构；此时析构再抛异常就是"异常嵌套"——标准规定直接 terminate。所以析构必须标 noexcept，内部异常自己吞掉（try-catch 包住，记日志不外抛）。

**Q：异常处理的性能开销？**
现代编译器是"零开销异常"（zero-cost exception）：正常路径零开销，只有真抛异常才付出代价（栈展开、查 catch 块）。因此异常适合"异常情况"——错误概率高（每次循环都可能触发）用错误码更划算；真正的异常情况（内存耗尽）用异常没负担。

### 11. C++20 协程

**场景还原**："C++ 协程是什么？怎么实现？和线程什么区别？"——答"可以暂停恢复的函数"就到顶了。面试官想听的是协程执行流程、三大核心组件的分工、与线程的真实差异。

#### 三句话版本

协程是能**暂停并在之后恢复**的函数，C++20 用三个关键字实现：co_await、co_yield、co_return。核心组件三件套：**Promise 对象**控制协程生命周期与返回值；**Coroutine Handle** 是恢复/销毁协程的句柄；**Awaiter** 定义 co_await 的等待行为。与线程的本质区别：线程由内核调度、切换成本高；协程由用户态自调度、切换成本极低，但不能真正并行。

#### 展开讲

**协程的执行流程**。协程被调用时不像普通函数一口气跑完，生命周期如下：

1. 分配协程帧（堆上，存局部变量、参数、恢复点）
2. 创建 Promise 对象
3. 调 promise.get_return_object() 拿到返回给调用者的对象
4. 执行协程体，遇 co_await / co_yield 暂停、控制权交还调用者
5. 调用者经 handle.resume() 恢复，或 handle.destroy() 销毁

关键点：暂停时协程的完整执行状态（局部变量、执行位置）都存在协程帧里，恢复时从断点续跑、无需重新初始化。

**协程 vs 线程 vs 回调**：

- **线程**：内核调度、支持真并行，但上下文切换要保存/恢复寄存器、切栈，微秒级开销
- **协程**：用户态调度、协作式多任务，切换只保存几个指针、纳秒级开销；但同一时刻只有一个协程在跑
- **回调**：逻辑被切碎、回调地狱、错误处理复杂；协程用线性代码写异步逻辑，可读性碾压

**适用场景**：异步 I/O（网络请求、文件读写）、生成器（大数据集流式处理）、状态机（复杂状态转换）、游戏开发（角色行为序列）。

#### 高频追问

**Q：协程帧里存了什么？**
Promise 对象、函数参数副本、所有局部变量、当前挂起点位置。本质是堆上一个结构体，保存协程"冻结"时的全部状态。

**Q：co_await 的三阶段流程？**
await_ready()——结果是否已就绪（就绪就不挂起）；await_suspend()——挂起协程、把 handle 交出去由别人恢复；await_resume()——恢复后取结果继续。

**Q：怎么避免协程内存泄漏？**
核心：确保 coroutine_handle 一定会被 destroy。实践：RAII 包装器（析构自动 destroy）、final_suspend 返回 suspend_always 由持有者负责销毁、避免 handle 循环引用。

**Q：协程能替代线程吗？**
不能。协程解决的是"异步代码难写难看"，不是并行计算。CPU 密集任务仍需线程/线程池；协程主攻 I/O 密集场景。

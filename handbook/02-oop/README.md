### 1. 构造函数六形态

**场景还原**：被问"C++ 构造函数有几种"，很多人能报出默认构造和拷贝构造，一到移动构造、委托构造、继承构造就含糊，更说不清编译器何时自动生成、何时罢工。这题考的是对对象初始化机制的全景认知。

#### 三句话版本

C++ 构造函数六个主要形态：默认构造、参数化构造、拷贝构造、移动构造（C++11）、委托构造（C++11）、继承构造（C++11）。它们的差别集中在触发时机与资源处理方式：默认构造做零初始化，拷贝构造复制资源，移动构造转移资源所有权，委托构造复用初始化逻辑，继承构造透传基类初始化。

#### 全景对照表

| 类型 | 形式 | 职责 | 编译器自动生成？ |
| --- | --- | --- | --- |
| 默认构造 | `ClassName()` | 无参创建，默认初始化 | 未定义任何构造函数时生成；定义了其他构造后需 `= default` 显式补回 |
| 参数化构造 | `ClassName(int x, ...)` | 带参创建 | 不自动生成 |
| 拷贝构造 | `ClassName(const ClassName&)` | 用已有对象初始化新对象 | 未定义时自动生成（按成员浅拷贝） |
| 移动构造 | `ClassName(ClassName&&)` | 窃取临时对象的资源 | 未定义拷贝/移动且未定义析构时自动生成 |
| 委托构造 | `C() : C(0,0) {}` | 一个构造调用同类另一个构造，消除重复代码 | 不自动生成 |
| 继承构造 | `using Base::Base;` | 派生类直接继承基类构造函数 | 需显式 using 声明 |

前四种解决"怎么创建对象"，后两种解决"怎么复用初始化逻辑"。其中移动构造是 C++11 性能优化的核心抓手，面试必问。

#### 高频追问

**Q：为什么要有移动构造？**
避免对临时对象深拷贝资源——直接"偷"过来。典型场景是 vector 扩容搬迁元素：移动构造只转移内部指针，不复制整块内存，速度远超拷贝构造。

**Q：拷贝构造的参数为什么必须是 const 引用？**
若按值传参，调用拷贝构造时还得先拷贝实参，无限递归。加 const 是为了能接住常量对象与临时对象。

**Q：什么时候编译器不再给你默认构造？**
只要手动定义了任意一个构造函数，默认构造就没了。想要回来只能自己写 `ClassName() = default;`。

### 2. 构造/析构与虚函数

**场景还原**：标准答案"构造不能、析构可以"人人会背，但追问"为什么构造不能""虚表指针何时建立""不用虚析构会炸成什么样"，能答透的不多。核心在于 vptr 的建立时机与多态删除的析构链。

#### 三句话版本

构造函数不能是虚函数：虚函数机制依赖"已就绪的 vptr"，而构造执行期间 vptr 尚未建立，机制无从运转。析构函数可以且（作为基类时）应该声明为虚函数：保证经基类指针删除派生类对象时，整条析构链被完整执行，资源不泄漏。

#### 对照表

| 维度 | 构造函数 | 析构函数 |
| --- | --- | --- |
| 定义 | 与类同名、无返回值，对象创建时自动调 | `~类名`，无参无返回值，对象销毁时自动调 |
| 能否为虚 | 不能 | 能，且基类必须虚 |
| 原因 | 构造期 vptr 未建立，虚机制不工作 | 非虚时基类指针 delete 派生类对象只调基类析构，派生类资源泄漏 |
| 调用顺序 | 基类 → 成员 → 派生类 | 派生类 → 成员 → 基类（与构造互逆） |
| 特殊行为 | 构造中调虚函数静态绑定到当前类版本，无多态 | 纯虚析构可使类成为抽象类，但必须提供实现体 |

一句话收束：构造时 vptr 没准备好，构造函数没法虚；析构时不虚，多态删除就会漏掉派生类的清理步骤。

#### 高频追问

**Q：什么情况下必须虚析构？**
只要类可能被继承、且可能通过基类指针 delete 派生类对象——析构就该是虚的。换句话说，"设计为基类"的类，虚析构是标配。

**Q：构造函数里调虚函数会怎样？**
能编译、能执行，但**没有多态**：只会调当前正在构造的那个类的版本。因为此刻派生类部分尚未构造，vptr 指向的是当前类的虚表。

**Q：析构函数里抛异常会怎样？**
非常危险。若析构发生在栈展开过程中（正在处理另一个异常），再抛异常会直接 `std::terminate`。所以析构函数应当吞掉一切内部异常——记日志可以，往外抛不行。

### 3. 重载与重写

**场景还原**：基线答案"重载参数不同、重写子类覆盖父类"人人会背。追问"重载能靠返回值区分吗""父类不加 virtual 会怎样""override 关键字到底防什么"，很多人就露馅了。本题的主线是：重载在编译期定案，重写在运行期定案。

#### 三句话版本

**重载（Overload）**发生在同一作用域：函数名相同、参数列表不同（类型/个数/顺序），编译器按实参在编译期选出目标——静态绑定。**重写（Override）**发生在继承体系：子类重新实现父类虚函数，签名完全一致，运行时按对象实际类型（虚表）决定调用谁——动态绑定。

#### 展开讲

**重载的成立条件**：同一作用域（同类或同命名空间）+ 函数名相同 + 参数列表必须不同。编译器只靠参数列表分辨，这在编译期就敲定。注意：**返回值类型不参与重载决议**——调用处编译器看不到返回值要赋给谁（甚至可能根本不用返回值），所以无法凭返回值区分。

**重写的成立条件**：三件套缺一不可——存在继承关系、父类函数标了 `virtual`、子类函数签名完全一致（函数名、参数、const 修饰全部对齐）。满足后，通过基类指针/引用调用时，运行期按实际类型走虚表选版本。

**virtual 的作用**：标在父类函数前，宣告"此函数可被重写，请走虚表机制"。父类不加 virtual，子类写同名同参函数不算重写，叫**隐藏（hiding）**——经基类指针调用永远命中父类版本，多态失效。

**override 的作用**（C++11）：写在子类函数后，请编译器核对"我真的在重写父类虚函数吗"。签名拼错、参数不匹配，编译器直接报错。不写 override 也能重写成功，但写了属于防御性编程，能把低级错误拦在编译期。

**不加 virtual 的后果**：父类无 virtual 时，子类同名同参函数构成隐藏而非重写——经父类指针调父类版本，经子类对象调子类版本。这是面试高频坑："子类写了同名函数"≠"重写"，没有 virtual 就没有多态。

#### 高频追问

**Q：重载能靠返回值区分吗？**
不能。标准规定重载决议只看参数列表。`func(1)` 调用处编译器能看见参数是 int，但看不见返回值去向，无从分辨。

**Q：重写的返回值必须完全一致吗？**
存在一个例外——**协变返回类型**：父类虚函数返回 `Base*`，子类重写时可返回 `Derived*`（Derived 继承自 Base）。除此之外必须完全一致。

**Q：重载和重写能共存吗？**
能。一个类里可以有多个同名函数（重载），其中某个虚函数同时被重写。两者是不同维度的概念，互不冲突。

**Q："隐藏"到底是什么？**
子类定义了与父类同名的函数（无论参数是否相同），只要不构成重写（父类非虚，或参数列表不同），父类版本就被遮蔽——子类对象只能看到自己的版本。隐藏不是多态机制，只是名字遮蔽。

### 4. 多态实现机制

**场景还原**："C++ 多态怎么实现的？"——答"虚函数+继承"只能拿三分之一的分。面试官想听的完整版是：vtable 放在哪、vptr 何时初始化、一次虚调用在底层走了几步。只背概念，一定会被追问到哑火。

#### 三句话版本

C++ 多态两条路线：**编译期多态**靠重载与模板，编译期敲定目标；**运行期多态**靠 virtual + 继承 + 基类指针/引用，运行期沿"vptr → vtable → 函数地址"链路动态绑定。

#### 两条路线对照

| 维度 | 编译期多态 | 运行期多态 |
| --- | --- | --- |
| 实现手段 | 重载、模板 | 虚函数 + 继承 |
| 绑定时机 | 编译期（静态绑定） | 运行期（动态绑定） |
| 关键机制 | 编译器按参数/模板实参选择 | vptr → vtable → 函数地址 |
| 触发条件 | 直接调用即可 | 必须经基类指针或引用调用 |
| 性能 | 零开销、可内联 | 一次间接寻址，无法内联 |
| 典型场景 | sort 比较器、max<T> | 基类接口统一调度派生类行为 |

**运行期多态三要素**：基类声明 virtual、派生类重写、经基类指针或引用调用。三者缺一即失效——用派生类对象直接调用时，编译器静态绑定，根本不查虚表。

**底层调用链**（以 `Animal* p = new Dog(); p->speak();` 为例）：

1. 编译器为每个含虚函数的类生成 vtable，槽位按声明顺序存放虚函数地址；Dog 的 speak 槽位填的是 `Dog::speak` 的地址
2. 每个对象内存头部藏一个 vptr，构造时指向本类的 vtable
3. `p->speak()` 展开为：经 p 找到 Dog 对象 → 读 vptr → 按 speak 的槽位偏移取地址 → 跳转执行

由此也能推导出一条铁律：**基类析构函数必须是 virtual**，否则 `delete p` 只执行基类析构，派生类资源泄漏。

#### 高频追问

**Q：抽象类与纯虚函数什么关系？**
含纯虚函数（`virtual void run() = 0;`）的类即抽象类，禁止实例化、只可被继承；派生类必须实现全部纯虚函数才能实例化——相当于语言强制的接口契约。

**Q：override 与 final 各管什么？**
override 请编译器核对"我真的重写了基类虚函数"，签名写错直接报错；final 禁止派生类继续重写某虚函数，或禁止整个类被继承。

**Q：虚调用比普通调用慢多少？**
多一次间接寻址（取 vptr + 查表），现代 CPU 上只差几纳秒；真正的代价是虚函数无法被内联。热路径上频繁调用的小虚函数，可用 CRTP 静态多态替代。

**Q：构造函数里能调虚函数吗？**
能调，但无多态。构造执行时 vptr 指向"当前正在构造的类"的虚表，不是最终派生类的——基类构造里调虚函数，命中的是基类版本。

### 5. 虚函数与纯虚函数

**场景还原**："两者有什么区别、什么时候用哪个？"——答"纯虚函数加 =0"只是字面差异。面试官真正想听的是**设计意图**的差别，以及"纯虚函数能不能有实现体"这类反转追问。

#### 三句话版本

虚函数用 `virtual` 声明、带默认实现，派生类可重写可不重写，类可实例化。纯虚函数声明末尾加 `= 0`、无默认实现，派生类必须重写，类不可实例化（抽象类）。一句话：虚函数说"我有默认行为，你可以改"；纯虚函数说"我只定规范，你必须自己写"。

#### 展开讲

**虚函数：给默认，留余地。** 经基类指针/引用调用时走动态绑定，按实际类型选版本。派生类不重写就沿用基类默认实现。类可以正常实例化。适合"大多数派生类行为一致、少数需要定制"的场景。

**纯虚函数：只立规矩，不给实现。** `= 0` 告诉编译器"本函数无默认实现，派生类必须自写"。含纯虚函数的类自动成为抽象类，无法直接 new。设计意图是定义接口契约——基类只规定"做什么"，"怎么做"完全交给派生类。

#### 核心区别表

| 维度 | 虚函数 | 纯虚函数 |
| --- | --- | --- |
| 声明形式 | `virtual void f() {}` | `virtual void f() = 0;` |
| 默认实现 | 有，派生类可不重写 | 无，派生类必须重写 |
| 类可否实例化 | 可 | 不可（抽象类） |
| 设计意图 | 提供默认行为，允许定制 | 定义接口规范，强制实现 |
| 典型场景 | 多数派生类行为相同 | 每个派生类行为都不同 |

#### 高频追问

**Q：构造函数能是虚函数吗？**
不能。虚调用依赖 vptr，而 vptr 在构造过程中才被设置——"构造函数负责把对象建出来"与"虚机制要求对象已存在"顺序矛盾。

**Q：纯虚函数能有函数体吗？**
能。`= 0` 只约束"派生类必须重写"，不禁止基类提供实现。基类可在类外写实现体，派生类经 `Base::f()` 显式调用。典型用途：给派生类一个可复用的兜底逻辑。

**Q：override 与 final 分别解决什么？**
override 请编译器核对重写的签名是否匹配，防"以为重写了其实没有"；final 禁止继续重写或禁止继承。两者都是 C++11 引入的编译期检查。

**Q：什么时候该用纯虚函数？**
基类只清楚"要做什么"、无法给出合理默认"怎么做"时。例：Shape 基类的 `draw()`，每种形状画法不同，没有合理默认——纯虚。若多数派生类行为一致、仅少数定制，普通虚函数给默认实现更合适。

### 6. 虚函数底层实现

**场景还原**："虚函数怎么实现的？一次虚调用底层发生了什么？"——只会说"虚函数表"三个字就到顶了。要拿满分，必须讲清 vtable 在哪、vptr 何时初始化、调用链怎么走。

#### 三句话版本

编译器为每个含虚函数的类生成一张 **vtable**，存放该类各虚函数的地址；每个对象内部藏一个 **vptr**，指向所属类的 vtable。经基类指针调用虚函数时，运行期沿"对象 → vptr → vtable → 函数地址"取地址跳转——这就是动态绑定的全部机关。

#### 展开讲

**vtable：类级的一张表。** 类里出现 virtual 函数，编译器就为该类生成一张 vtable，槽位按声明顺序排布。派生类重写了某个虚函数，它的 vtable 对应槽位换成自己的地址；没重写的槽位继续指向基类版本。

**vptr：对象级的一个指针。** 每个含虚函数的对象在内存布局里多一个隐藏成员 vptr，构造函数执行时被编译器自动设为指向当前类的 vtable。所以 `Base* p = new Derived();` 后，p 所指对象的 vptr 指向 Derived 的虚表，不是 Base 的。

**调用链路。** `p->show()` 在底层展开：取对象 vptr → 按 show 的槽位偏移取函数地址 → 间接跳转。相比普通调用多一次解引用，这正是虚函数"慢一点"的来源。

核心一句话：**vtable 把"调哪个函数"从编译期写死，变成运行期查表。**

#### 高频追问

**Q：vptr 放在对象哪个位置？**
主流实现（GCC/Clang/MSVC）统一放在对象内存最前端——凭首地址就能直接取 vptr，省掉偏移计算。

**Q：多继承下 vtable 怎么安排？**
一个对象可能持有多个 vptr——每条继承链一个，对应多张虚表。经不同基类指针调用虚函数，走的是各自那条链的 vptr/vtable。

**Q：虚调用比普通调用慢多少？**
通常就是"一条 mov + 一条间接 call"的差距，现代 CPU 有分支预测与缓存，差距很小。真正的性能损失在编译器无法内联虚函数，丧失内联优化机会。

**Q：基类析构为什么必须 virtual？**
`delete basePtr` 时若析构非虚，只执行基类析构，派生类析构不运行，其持有的资源泄漏。声明为 virtual 后，析构同样走虚表，能正确命中派生类版本。

### 7. 多重继承与菱形继承

**场景还原**：答"虚继承"三个字只是开头。追问"虚继承的内存布局长什么样""为什么虚基类必须由最派生类初始化""多重继承和组合怎么选"，答得出这些，才算真理解菱形继承在内存层面捅的娄子。

#### 三句话版本

多重继承让一个类同时继承多个基类：好处是组合多个能力，坏处是基类同名成员产生二义性，最严重的是**菱形继承**——D 继承 B、C，而 B、C 都继承 A，导致 D 里出现**两份 A 子对象**，访问 A 的成员不知用哪份。C++ 用**虚继承**化解：B、C 虚继承 A，编译器保证 D 中只有一份 A，经虚基类指针间接访问。

#### 展开讲

**菱形继承到底错在哪。** 普通多重继承下，D 的内存里装着完整的 B 子对象和完整的 C 子对象；B 里有 A，C 里也有 A——D 里就有两份 A。两宗罪：其一，A 的数据存了两份，浪费内存；其二，访问 A 的成员时编译器分不清走 B 路径还是 C 路径，必须显式写 `d.B::name` 或 `d.C::name`。

**虚继承怎么修。** B、C 以 `virtual public A` 继承时，编译器不再把 A 子对象嵌进 B、C 内部，而是在两者里各放一个**虚基类指针（vbptr）**，指向虚基类表（vbtable），表里记录 A 子对象相对当前对象的偏移。最终 D 的布局里只有一份 A，B、C 经各自 vbptr 间接访问这份共享 A。代价：访问虚基类成员多一次间接寻址，对象体积多出 vbptr 的开销。

**为什么虚基类要由最派生类初始化。** 普通继承下，B 的构造函数负责初始化自己的 A 子对象；虚继承下 A 只有一份，B、C 都去初始化就冲突了。所以 C++ 规定：虚基类由最派生类（D）的构造函数直接初始化，B、C 构造函数初始化列表中对 A 的初始化被忽略。

#### 高频追问

**Q：什么时候用多重继承，什么时候用组合？**
多重继承只适合"接口组合"——多个基类都是纯虚接口、无数据成员。基类带数据与实现逻辑时，优先组合（把基类作为成员变量），避开菱形继承与复杂内存布局。经验法则：继承表达 is-a，组合表达 has-a。

**Q：名称冲突怎么处理？**
用作用域解析显式指定：`d.B::func()` 或 `d.C::func()`；或者在派生类里重写同名函数，内部决定转发给哪个基类。

**Q：多重继承下析构要注意什么？**
基类析构必须 virtual，否则经基类指针 delete 派生类对象时派生类析构不执行，资源泄漏。编译器会按继承声明的逆序自动调用各基类析构，无需手动。

**Q：Java/Go 为什么砍掉多重继承？**
Java 用 interface 替代——可实现多接口、只继承一个类，从语言层面杜绝菱形问题；Go 干脆只有组合+接口，没有继承。C++ 保留多重继承图的是灵活性，工程实践建议仅限接口组合场景。

### 8. 禁止类被继承

**场景还原**：答出 `final` 只拿基础分。追问"final 还能干什么""为什么要禁止继承""C++11 之前怎么办"，考的是面向对象设计意识——什么时候该开放继承，什么时候该焊死。

#### 三句话版本

C++11 起直接用 `final` 修饰类：`class MyClass final { ... };`，编译器解析继承时发现目标是 final 类即报错，零运行时开销。final 还能修饰虚函数，禁止派生类继续重写。C++11 之前的"私有构造 + 虚继承 + 友元"组合 hack 已被时代淘汰，了解即可。

#### 展开讲

**final 的两种用法**

1. 修饰类：禁止任何类继承它。
2. 修饰虚函数：`void speak() final;`，禁止派生类重写该虚函数。

两者都是编译期静态检查，零运行时开销。原理很直白——编译器在解析继承关系或虚函数重写时检查 final 标记，命中即报编译错误，不需要任何运行时机制。

**C++11 之前的替代方案（仅作历史了解）**。思路是利用虚继承的规则："虚基类必须由最派生类直接调用构造函数"。做法：定义辅助类 MakeFinal，构造函数设为 private；目标类虚继承 MakeFinal 并声明其为友元。目标类自己是友元、能正常构造；任何人想继承目标类，最终派生类就得直接调用 MakeFinal 的私有构造——访问不到，编译报错。这个方案链路复杂、可读性差，现在毫无必要。

#### 高频追问

**Q：final 在性能上有什么收益？**
编译器确认类为 final 或虚函数为 final 后，可执行**去虚拟化（devirtualization）**：既然不可能有派生类重写，调用目标在编译期就确定，虚调用（vptr 间接跳转）可优化为直接调用甚至内联。热路径上频繁调用的小虚函数标 final，收益明显。

**Q：什么场景该禁止继承？**
工具类（只有静态方法，无状态，继承无意义）、策略类（该组合而非继承）、资源句柄类（如文件描述符包装，继承会破坏 RAII 语义）、性能关键类（final 帮编译器优化）。底层原则：组合优于继承——类的设计意图是被组合使用而非被继承扩展时，用 final 把意图写明。

**Q：final 和 override 什么关系？**
都是 C++11 的上下文关键字，围绕虚函数工作：override 申明"我确实在重写"，签名写错报错；final 申明"到此为止，不许再重写"。两者可叠加：`void speak() override final;` 表示"我重写了基类的 speak，且禁止后续派生类再重写"。

### 9. 深拷贝与浅拷贝

**场景还原**："深浅拷贝有什么区别、什么时候必须深拷贝？"——答"浅拷贝复制指针、深拷贝复制内容"只值一半分。追问"为什么会双重释放""STL 容器存自定义对象有什么坑""COW 是什么"，才见真章。

#### 三句话版本

**浅拷贝**只复制成员变量值：指针成员复制的是地址，两个对象的指针指向同一块堆内存。**深拷贝**为指针成员重新分配内存并复制内容，两个对象各持独立内存。核心风险在浅拷贝：任一对象析构 delete 这块共享内存，另一对象的指针立刻悬垂——再 delete 就是双重释放，程序崩溃。

#### 展开讲

**编译器默认生成的拷贝是浅拷贝。** 自动生成的拷贝构造与赋值运算符执行逐成员复制：对 int、double 这类值类型没问题；对指针成员，复制的只是地址值——两个对象指向同一块内存。

**浅拷贝的三种死法**（类管理动态内存时）：

- 双重释放：两对象析构时各 delete 一次同一块内存 → 崩溃
- 悬垂指针：一方析构后，另一方的指针指向已释放内存 → 未定义行为
- 意外修改：经一个对象改数据，另一个对象的数据跟着变

**深拷贝怎么做。** 类含裸指针且自己管理内存时，必须手写三件套：拷贝构造、赋值运算符、析构函数——这就是 **Rule of Three**。拷贝构造/赋值里为指针成员 new 新内存并复制内容，两对象各管各的内存、各释放各的。

**现代 C++ 的替代方案。** C++11 后用智能指针管理动态内存即可免手写：unique_ptr 禁止拷贝、只许移动，从根源上杜绝共享；shared_ptr 用引用计数管理生命周期，多个对象可安全共享同一块内存。

#### 高频追问

**Q：什么时候必须手写深拷贝？**
类里有裸指针（T*）且这块内存是类自己 new 出来的。判断口诀：写了含 delete 的析构函数，就必须写拷贝构造和赋值运算符。类里只有值成员或智能指针时，编译器默认拷贝就够。

**Q：STL 容器存自定义对象有什么坑？**
容器是值语义，push_back 触发拷贝构造。若类有裸指针却没写深拷贝，容器内对象与外部对象共享内存；容器扩容搬迁旧元素析构时释放内存，新元素的指针直接悬空——崩溃。解法：实现深拷贝，或改用智能指针管理资源，或容器存指针。

**Q：写时复制（COW）是什么？**
一种优化策略：拷贝时先浅拷贝共享内存，某方要修改时才真正深拷贝。用引用计数记录共享者数量，修改前检查——计数大于 1 就先复制再改。早期 std::string 用过 COW，但多线程下引用计数的原子操作开销太大，C++11 起标准库弃用。

**Q：移动语义和深拷贝什么关系？**
移动语义是 C++11 给出的第三条路：既不浅拷贝（共享）、也不深拷贝（复制），而是**转移所有权**。移动构造把源对象指针"偷"过来并置空源指针，代价从 O(n) 降到 O(1)。源对象不再需要时（函数返回临时对象），移动远比深拷贝划算。

### 10. this 指针

**场景还原**："this 是什么？"——"指向当前对象的指针"这个答案只能过初筛。追问"this 存在哪""编译器怎么传它""const 成员函数里 this 是什么类型""this 能为空吗"，能不能答顺，取决于你是否明白：this 没有任何神秘感，它就是编译器自动塞进来的第一个参数。

#### 三句话版本

this 是编译器隐式传给每个非静态成员函数的第一个参数，类型为 `T* const`（指针本身不可变，所指对象可变）。`obj.func(x)` 在编译器眼里就是 `func(&obj, x)`——对象地址作为第一个实参。this 通常走寄存器传递（x86 的 thiscall 用 ecx），不占栈空间；const 成员函数里 this 变成 `const T* const`，所以不能改成员；静态成员函数没有 this，因为它不绑定任何对象。

#### 展开讲

**编译器的"魔法"就是一次改写。** 成员函数调用编译后与普通函数无异：`obj.func(a, b)` 被改写成 `func(&obj, a, b)` 的形式，对象地址充当第一个隐含实参——这就是 this。它不存于对象内部，也不是什么运行时机关，就是个函数参数。

**this 的类型分两种**。普通成员函数中是 `T* const`：指针自身常量（不能让它指向别的对象），所指对象非常量（可改成员）。const 成员函数中是 `const T* const`：指针与对象双双只读，任何非 mutable 成员都不能改。

**this 存在哪里**。它是函数参数，具体去向由调用约定决定：x86 的 thiscall 约定经 ecx 寄存器传递、不占栈空间；x64 与 ARM 通常也用寄存器传前几个参数。只有函数内部需要取 this 的地址时，编译器才把它溢出到栈上。

**静态成员函数为什么没有 this**。静态函数属于类而非对象实例，调用时不需要对象（`T::staticFunc()`），编译器不传对象地址——没有 this。这也解释了静态函数为何访问不了非静态成员：没有对象地址，就无法定位成员内存。

#### 高频追问

**Q：return *this 是什么操作？**
解引用 this 得到当前对象本身（类型 T&），返回它即返回对象引用。链式调用 `obj.set(1).set(2).set(3)` 正靠每个方法 `return *this` 支撑——每次返回同一对象的引用，才能继续调下一环。

**Q：this 能是 nullptr 吗？**
语法上能造出来（`((T*)nullptr)->func()`），但这是未定义行为。若函数体内不碰任何成员，个别编译器下可能不崩——纯属侥幸，不能依赖。凡经空 this 访问成员，都是段错误。

**Q：this 与智能指针有什么牵扯？**
this 是裸指针、不管生命周期。想在对象内部拿到指向自身的 shared_ptr，直接 `shared_ptr<T>(this)` 会造成双重释放；正确姿势是继承 `std::enable_shared_from_this<T>` 再调 `shared_from_this()`。

**Q：为什么构造函数里调虚函数没有多态？**
构造执行时对象的动态类型还是"当前正在构造的类"——vptr 指向当前类虚表，this 的静态类型也是当前类。所以虚函数只会命中当前类版本，派生类的重写版本根本排不上号。

### 11. 单例模式

**场景还原**："怎么实现单例？"——能写懒汉式只是起点。追问"线程安全吗""双检锁有什么坑""现代 C++ 推荐哪种"，考的是你清不清楚四种实现各自的坑、以及演进到 Magic Static 的完整逻辑链。

#### 三句话版本

单例 = 全类仅一个实例 + 全局访问点。实现三板斧：构造函数私有化 + 删除拷贝/赋值 + 静态方法返回唯一实例。现代 C++ 的标准答案是**局部静态变量（Magic Static）**：`static Singleton& getInstance() { static Singleton inst; return inst; }`——C++11 保证局部 static 初始化线程安全，代码最短、自动析构、零坑。

#### 四种实现的演进逻辑

**饿汉式**：程序启动即创建（静态成员在 main 之前初始化）。天然线程安全，但单例过重且可能用不上时白占资源；多个饿汉单例之间的初始化顺序还不确定（static initialization order fiasco）。

**懒汉式**：首次调用 getInstance() 才创建。解决资源浪费，但多线程下两个线程同时判定 `instance == nullptr` 会各建一份——线程不安全。

**双检锁（DCLP）**：懒汉式加锁。第一次检查避免每次加锁（保性能），加锁后二次检查防重复创建。但 C++11 之前受指令重排与内存可见性影响，DCLP 实际带 bug；C++11 后需配合 `std::atomic` 或 `std::call_once` 才能写对。

**Magic Static（C++11 推荐）**：函数内局部 static 变量，标准规定其初始化线程安全（编译器负责加锁）。一行代码，无手动锁、无裸指针、程序结束自动析构——现代 C++ 的标准答案。

**为什么 Magic Static 是最优解**：线程安全由编译器兜底；返回引用而非指针，没有 delete 问题；程序结束自动析构；代码极简不易写错。唯一"缺点"是无法控制销毁顺序——但绝大多数场景根本用不上这能力。

#### 高频追问

**Q：单例什么时候不该用？**
单例本质是全局状态，代价包括：单元测试难隔离、依赖关系被隐藏（调用方看不出它用了单例）、违背单一职责（既管业务又管自己的生命周期）。能用依赖注入替代就别用单例。真正合适的场景：日志器、配置管理、线程池、连接池——天然全局唯一且生命周期贯穿程序。

**Q：双检锁在 C++11 之前为什么是坏的？**
`instance = new Singleton()` 实际分三步：分配内存 → 构造函数 → 赋值指针。编译器/CPU 可能重排为"分配 → 赋值 → 构造"，另一线程看到指针非空就直接返回，但对象还没构造完——未定义行为。C++11 的 atomic 与内存序能修，但代码繁琐，不如 Magic Static 一劳永逸。

**Q：饿汉式的初始化顺序坑在哪？**
单例 A 的构造函数里用到了单例 B，而 B 属于另一个编译单元、还没初始化——直接崩。Magic Static 天然免疫：谁先被调用谁先初始化，顺序由调用链决定。

**Q：单例怎么正确销毁？**
Magic Static 程序结束自动析构，无需人工管理。指针式实现（饿汉/懒汉/双检锁）得另配销毁机制（如 atexit 注册回调），否则泄漏——这也是 Magic Static 受推荐的原因之一。

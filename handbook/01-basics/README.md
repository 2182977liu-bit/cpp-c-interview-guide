### 1. C++ 三大特性

**场景还原**：技术面开场白里，"三大特性"几乎是必考题。如果只憋出"封装、继承、多态"六个字，这场面试基本就凉了一半——面试官真正想验证的，是你能否讲清每个特性"解决什么矛盾"，以及多态在机器层面到底怎么落地。

#### 三句话版本

- **封装**：把数据与操作捆进类，靠访问限定符（`public`/`private`/`protected`）划清内外边界，调用方只能走公开接口，碰不到内部状态。
- **继承**：派生类沿用基类的成员与行为，在既有能力之上做扩展，消除重复代码。
- **多态**：同一接口、不同对象、不同表现。它有两条实现路线——编译期多态（重载、模板）与运行期多态（虚函数）。

#### 展开讲

**封装的意义在于"藏"。** `private` 成员对外不可见，`protected` 对子类开放，`public` 对所有人开放。把状态藏起来之后，类的作者可以随意改内部实现而不惊动调用方——这是大型工程能够持续演进的基础。

**继承的意义在于"复用"。** 派生类天然持有基类的非私有成员，并能重写基类方法改变行为。经典的 Animal → Dog/Cat 例子里，name 属性只写一份，`speak()` 各自实现。继承方式有 `public`、`protected`、`private` 三种，差别在于基类成员"进入派生类后"的访问等级如何变化，日常工程里 `public` 继承占绝对多数。

**多态的意义在于"同一个抽象，多种实现"。**

- **编译期多态（静态绑定）**：重载函数、运算符重载、模板。编译时就把目标敲定，运行期零开销。
- **运行期多态（动态绑定）**：虚函数 + 继承。基类指针或引用指向派生类对象时，实际执行的是派生类版本。

运行期多态的机器级实现是这场对话的胜负手：

1. 只要一个类声明了虚函数，编译器就为**这个类**生成一张 **vtable**（虚函数表），表里按声明顺序存放虚函数地址；
2. 该类的**每个对象**头部藏一个 **vptr**（虚表指针），构造时指向本类的 vtable；
3. 用基类指针调用虚函数时，运行期按"对象 → vptr → vtable → 函数地址"的链路取地址并跳转。

注意粒度差异：vtable 是**类级**的（同类对象共享一张表），vptr 是**对象级**的（每个对象都带一个）。

#### 高频追问

**Q：编译期多态能彻底取代运行期多态吗？**
替代不了。模板要求类型在编译期确定，适合"类型已知、行为不同"；虚函数适合"类型到运行期才出现"的场景，比如工厂函数返回基类指针。若类型编译期能定、又想省掉虚表开销，可以上 CRTP（奇异递归模板）做静态多态。

**Q：手推一遍 vtable 调用过程？**
`Animal* a = new Dog();` 这行执行完，Dog 对象头部的 vptr 指向 Dog 的虚表。随后 `a->speak()` 被编译成：读 a 的 vptr → 按 speak 在虚表中的槽位偏移取函数地址 → call。虽然 `a` 的静态类型是 `Animal*`，但实际执行的是 `Dog::speak`。

**Q：不用虚函数能做出运行期多态吗？**
可以，但都属于"绕路"：成员函数指针、`std::function` + 策略模式、类型擦除（type erasure）。标准库的 `std::function` 本质上就是一次类型擦除，实现了"无虚表的多态"，代价是额外开销和失去内联。

### 2. 指针与引用

**场景还原**：被问到"指针和引用的区别"，多数人能脱口而出"指针可空、引用不可空"，可一旦被追问"引用在内存里长什么样""const 修饰的口诀是什么""什么场景选谁"，回答就开始飘了。这道题测的是你对 C++ 内存模型的直觉。

#### 三句话版本

指针是一个**独立存在的、存地址的变量**：可以重赋值、可以为空、可以做算术，但解引用要自己负责。引用是**某个已有对象的别名**：出生即绑定、终生不改嫁、不允许悬空，语法上像普通变量一样用。

一个助记角度：指针记录"他家住哪条街"，引用干脆就是"他的另一个称呼"。

#### 全维度对照

| 对比项 | 指针 | 引用 |
| --- | --- | --- |
| 本体 | 存放地址的变量 | 对象的别名 |
| 独立内存 | 占 4/8 字节 | 语义上不占空间（编译器实现层可能借用指针） |
| 初始化 | 可以先声明后赋值 | 声明时必须绑定 |
| 空值 | 可以是 `nullptr` | 不允许 |
| 换绑 | `p = &b` 随时切换 | 绑定后不可更改 |
| 二级形式 | 有 `int**` | 没有"引用的引用" |
| 算术 | 支持 `p++`、`p+n` | 没有 |
| 使用方式 | 必须 `*p` 解引用 | 直接当变量名用 |
| sizeof | 得到指针自身大小 | 得到被绑定对象的大小 |
| const 组合 | `const int*` / `int* const` / `const int* const` | `const int&` 表示"绑定到只读对象" |

**const 修饰指针的口诀**：`*` 左边的 const 管"值"（底层 const），`*` 右边的 const 管"指针本身"（顶层 const）。`const int* p` 值改不了、指向随便换；`int* const p` 指向焊死、值随便改。

**引用为什么没有"const 引用"这一说**：引用天生就不可换绑，等价于自带 const 属性。`const int& r` 里的 const 约束的是"被引用的那个对象"，不是引用自身。

#### 高频追问

**Q：引用真的不占内存？**
语义层面不占。编译器在实现上通常拿指针来存别名地址，但由于编译器保证引用非空、不换绑，这些约束在编译期就完成了检查；到机器码层面，引用和指针可能长得一模一样。

**Q：什么时候选指针，什么时候选引用？**
语义上"可能没有"（可空参数、查找失败返回空）→ 指针；语义上"需要中途换目标"（链表游标、遍历）→ 指针；其余一律引用——少判空、少悬垂、语法干净。现代 C++ 里裸指针的身影越来越少：要所有权用智能指针，只是"借用"就用引用。

**Q：传参时两者性能有差别吗？**
没有。最终生成的代码都是传地址，性能不是选择依据，语义才是：参数必然存在 → 引用；参数可能缺席 → 指针。

**Q：引用能绑临时对象吗？**
左值引用不能，但 `const T&` 可以绑临时对象并延长其生命周期；C++11 的右值引用 `T&&` 就是专门为临时对象设计的，是移动语义的入口。

### 3. struct 与 class

**场景还原**：这道题的及格答案是"默认访问权限不同"，但面试官往往还会追三刀：继承的默认权限呢？模板参数里能用 struct 吗？真实项目里你按什么标准二选一？三刀都接得住，才算真懂。

#### 三句话版本

在 C++ 里 struct 与 class 的**表达能力完全一致**，真正的差异只有两处默认值：struct 的成员与继承默认 `public`，class 默认 `private`。此外模板形参只接受 `class`/`typename`，写 `template<struct T>` 直接报语法错。工程惯例上，struct 表示"透明数据包"，class 表示"有封装逻辑的类型"。

#### 展开讲

**差异一：成员的默认访问级别。** struct 成员默认 `public`，外部可直接触碰；class 成员默认 `private`，必须经接口访问。注意两者都可以显式写全三种访问限定符——这只是"默认值"之争，不是能力之分。

**差异二：继承的默认访问级别。** `struct D : B` 默认 public 继承；`class D : B` 默认 private 继承，后者会把基类的 public 成员挡在派生类外面。实践中没人依赖默认继承权限，都会显式标注。

**差异三：模板形参的书写限制。** `template<class T>` 与 `template<typename T>` 等价合法，`template<struct T>` 非法。这是语法层面的硬规定。

**工程惯例（靠自觉，不靠编译器）**

- struct 适合：纯数据聚合，成员全公开，没有需要守护的不变量——配置结构体、坐标点、协议包头、POD。
- class 适合：内部状态需要接口来维护不变量——业务对象、资源句柄、带构造/析构行为的类型。

这套惯例的价值在团队协作：看到 struct 就默认"它是只读的透明袋子"，看到 class 就知道"进来走接口"。

#### 高频追问

**Q：struct 里能放 private 成员吗？**
能。语法能力完全对等，你甚至能在 struct 里写虚函数、构造函数。编译器不会拦你，但读代码的人会困惑——这属于"合法但反直觉"的写法。

**Q：什么是 POD？和 struct 什么关系？**
POD（Plain Old Data）指内存布局与 C 兼容的类型：无虚函数、无用户定义构造/析构、成员全 public、可安全 `memcpy`。struct 语义上就暗示"纯数据"，天然适合定义 POD；class 同样能定义出 POD，只要条件凑齐。

**Q：C 的 struct 和 C++ 的 struct 是一回事吗？**
不是。C 的 struct 只能装成员变量；C++ 出于兼容把 struct 扩展成了"默认 public 的 class"。做 `extern "C"` 混编时，共享结构体必须保持 C 兼容写法（不挂成员函数、不搞继承）。

**Q：为什么工程里几乎见不到 struct 继承？**
struct 的语义是"数据袋子"，继承暗示行为扩展与多态，两者互相打架。Google 风格指南也明确：仅当全部成员 public 且无虚函数时才用 struct。

### 4. struct 与 union

**场景还原**：答"struct 各存各的、union 共享一块"只能拿到一半分。追问"union 的 sizeof 怎么算""union 里能塞 std::string 吗""现在还需要 union 吗"——这三问才是分水岭。

#### 三句话版本

struct 的每个成员占据**独立地址**，sizeof ≈ 各成员之和（含对齐填充）；union 的所有成员**共用同一起始地址**，sizeof 取最大成员，任意时刻只有一个成员是"活的"。struct 拥有完整 OOP 能力；union 禁止继承、禁止虚函数、禁止引用成员且成员强制 public。C++11 起 union 允许放非 POD 成员，但构造/析构全靠手工 placement new + 手动调析构；C++17 的 `std::variant` 是它的类型安全替身。

#### 展开讲

**内存布局是本题的根。** `struct { int a; double b; char c; }` 三个成员依次排布、互不踩踏，整体 24 字节（含对齐）。`union { int a; double b; char c; }` 只占 8 字节（最大成员 double 决定），写入任一成员都会覆盖其余成员——这就是"同一时刻只活一个"的含义。

**能力清单对比。** struct 本质是"默认 public 的 class"：继承、虚函数、访问控制全都要。union 限制严格：不可继承也不可被继承、无虚函数、无引用成员、成员恒为 public，但允许自定义构造/析构和普通成员函数。

**C++11 之后 union 的变化。** 早期 union 只能放 POD。C++11 放开了这一限制，允许放 `std::string` 这类管理资源的成员——但 union 自身不知道"当前谁在活"，编译器不会替你调构造和析构，你必须自己 placement new 构造、自己显式调 `s.~basic_string()`，漏掉就是泄漏或未定义行为。

**现代答案：`std::variant`（C++17）。** variant 内部带类型标签，自动管理活跃类型的构造与析构，访问错类型时抛异常而非未定义行为。除非在极限内存/性能场景（嵌入式寄存器映射、二进制协议解析），否则现代 C++ 应优先 variant。

#### 高频追问

**Q：union 的 sizeof 公式？**
取最大成员的字节数，再按最大对齐值向上取整。`union { char c; double d; }` 是 8 字节，不是 1+8。

**Q：union 的实际用途？**
两个经典位置：其一，把同一块 buffer 按不同字段视角解释（网络包头、硬件寄存器映射）；其二，多个字段保证不同时使用，用共享存储省内存（嵌入式、高性能场景）。如今这两类需求分别有 `std::bit_cast` 和 `std::variant` 这类更安全的替代。

**Q：为什么往 union 里放 string 会出事？**
因为 union 不知道当前活跃成员是谁，析构时无从决定该调谁的析构函数：写入了 string 却不手动调 `s.~basic_string()` 就泄漏；活跃成员不是 string 却去调它的析构就是 UB。variant 用内部 tag 追踪活跃类型，自动接管生命周期，这正是它更可靠的原因。

**Q：union 的成员能加 private 吗？**
不能。struct 只是"默认 public"，union 是"永远 public"——访问控制修饰符在 union 里直接被语法拒绝。

### 5. static 与 const

**场景还原**：两者各自的作用很多人能背，可一旦问"static const 修饰同一个变量时语义如何叠加""static 局部变量初始化线程安全吗""不同编译单元的 static 初始化顺序有什么坑"，答案就开始模糊。这题的核心是把两条正交的语义轴拆开讲。

#### 三句话版本

**static 操控生命周期与可见性**：让局部变量跨调用存活、让全局符号只在当前文件可见、让类成员被所有对象共享。**const 操控可修改性**：变量只读、指针/引用不可通过它改值、成员函数承诺不改对象状态。两条轴互不干涉，可以叠加：`static const int X = 42;` 又共享又只读。

#### 展开讲

**static 的四张面孔**

1. **局部静态变量**：生命周期拉长到程序结束，作用域仍锁在函数内；只初始化一次，之后每次调用都保留上次的值。
2. **文件级 static**：把全局符号变成内部链接，其他 `.cpp` 无法 `extern` 到它——实现"文件私有"。
3. **静态成员变量**：挂在类上而非对象上，全体对象共享一份；必须在类外定义（C++17 后可用 `inline static` 类内完成）。
4. **静态成员函数**：没有 `this`，访问不了非静态成员，可以用 `类名::fn()` 直接调。

**const 的四张面孔**

1. **修饰变量**：赋值即编译报错。
2. **修饰指针**：const 在 `*` 左边 → 底层 const（所指内容只读）；在 `*` 右边 → 顶层 const（指针不换绑）；`const int* const p` 双重锁定。
3. **修饰引用**：`const int& ref = x` 表示不能经 ref 改 x，常用于传参——既免拷贝又防篡改。
4. **修饰成员函数**：承诺不改任何非 `mutable` 成员；const 对象只能调 const 成员函数。

**核心差异表**

| 维度 | static | const |
| --- | --- | --- |
| 核心语义 | 生命周期 + 可见性 | 只读性 |
| 修饰局部变量 | 存活到程序结束 | 值不可改 |
| 修饰全局变量 | 限制为文件内链接 | 默认文件内链接且只读 |
| 修饰类成员变量 | 全体对象共享一份 | 必须在初始化列表里初始化 |
| 修饰成员函数 | 无 this，可类名调用 | 不改成员，const 对象可调 |

#### 高频追问

**Q：const 和 constexpr 差在哪？**
const 是"运行期只读"，初值允许运行期才算出来；constexpr 是"编译期常量"，值必须编译期可算，可用于数组长度和模板实参。记住单向蕴含：constexpr 一定 const，const 未必 constexpr。

**Q：static 局部变量的初始化线程安全吗？**
C++11 起标准保证（magic statics）：编译器会加锁确保只有一个线程执行初始化。但注意——初始化**之后**的读写没有任何同步，多线程改它照样要自己加锁。Meyer's Singleton 正是建立在这条保证之上。

**Q：mutable 是干嘛的？**
给个别成员"开绿灯"：在 const 成员函数里也允许改它。典型用途：缓存、调用计数、`mutable std::mutex mtx_`。它不破坏逻辑 const——对象的可观察状态没变，变的只是内部实现细节。

**Q：const_cast 去 const 安全吗？**
只有一种情况合法：对象本身不是 const，只是被 const 指针/引用指到了。若对象生来就是 `const int x = 42;`，去 const 再写就是未定义行为——编译器可能把它优化成常量，你改了也白改。

**Q：跨编译单元的 static 初始化顺序有什么坑？**
这是著名的 Static Initialization Order Fiasco：不同 `.cpp` 的全局/静态变量初始化顺序未定义，A 文件的静态变量可能在 B 文件的静态变量就绪前就被使用。解法是 Construct On First Use——把全局对象换成函数内局部 static，首次访问时才构造。

**Q：C 和 C++ 的 const 有什么不一样？**
C 里 const 默认外部链接、不能当数组长度，本质是"只读变量"；C++ 里 const 默认内部链接，编译器尽量把它当编译期常量用，甚至可以定数组大小。C++ 的 const 更接近"真正的常量"。

### 6. extern "C"

**场景还原**："extern "C" 是干什么的？"——能答"C/C++ 混编用"只算入门。追问"名称修饰到底做了什么""为什么 C++ 必须修饰而 C 不用""extern "C" 改变了哪些底层约定"，能不能答顺，取决于你对链接机制的理解。

#### 三句话版本

`extern "C"` 命令 C++ 编译器：**对这些声明不做名称修饰（Name Mangling）**，符号名保持函数名原样。之所以需要它，是因为 C++ 支持重载，编译器必须把参数类型编进符号名（如 `void foo(int)` → `_Z3fooi`）来区分同名函数；而 C 没有重载，符号就是函数名本身。若 C++ 调 C 库时不加 extern "C"，编译器去找 `_Z3fooi`，C 库里只有 `foo`——链接器当场报 undefined reference。

#### 展开讲

**名称修饰是问题的源头。** C++ 允许同名不同参的重载，链接器面对目标文件时只能靠符号名区分，所以编译器把参数类型、命名空间等信息编码进符号：`void foo(int)` 变 `_Z3fooi`，`void foo(double)` 变 `_Z3food`。C 语言一个名字只对应一个函数，符号名 = 函数名，无需修饰。

**链接期对不上号。** C++ 调 C 库时，C++ 侧按修饰后的名字找符号，C 库里躺着的却是素名，两边凑不齐，链接失败。`extern "C"` 就是开关：声明处标上它，C++ 编译器按 C 规则生成符号引用（素名 `foo`），与 C 库一拍即合。

**调用约定也被捎带改变。** extern "C" 通常还意味着采用 C 调用约定（如 `__cdecl`）——参数如何压栈、栈由谁清理由约定决定。C/C++ 约定可能不一致，extern "C" 保证二进制层面严丝合缝。

**标配写法：`__cplusplus` 宏。** 通用头文件用 `#ifdef __cplusplus` 包住 extern "C"：C 编译器看不见这段（宏未定义），C++ 编译器看得见并正确处理，同一份头文件两边通吃。

#### 高频追问

**Q：为什么 C++ 必须修饰而 C 不用？**
根源是重载：同名多版本必须靠符号区分。此外命名空间、模板产生的符号同样要编码。C 无这些机制，素名即可。

**Q：extern "C" 能套在成员函数上吗？**
套不上。成员函数隐含 `this` 参数、依赖 C++ 对象模型，C 调用约定接不住。想让 C 调 C++ 类功能，惯用做法是写一个 `extern "C"` 的包装函数：内部 new 对象、调成员函数，对外只暴露 C 接口。

**Q：extern "C" 函数能重载吗？**
不能。不做修饰意味着符号名就是函数名，两个同名 extern "C" 函数（哪怕参数不同）在链接器眼里是重复定义。这也从反面解释了 C 语言为什么没有重载——它压根没有修饰机制。

**Q：实际项目里 extern "C" 出现在哪？**
三处：① C++ 调 C 库（glibc、SQLite、libpng），在库头文件的声明外裹 extern "C"；② C++ 写库给 C 用，导出接口时标 extern "C"；③ 跨语言扩展（Python/Lua 等），它们的 FFI 都是 C 风格，C++ 写扩展必须用 extern "C" 导出入口。

### 7. volatile 关键字

**场景还原**：嵌入式与后端面试都爱问 volatile。多数人只会说"防止编译器优化"，再追问"具体拦的是哪种优化""volatile 能不能当线程同步用"就哑火了。

#### 三句话版本

volatile 告诉编译器：这个变量的值可能被**程序之外的力量**改动（硬件寄存器、中断服务程序 ISR 等），所以**每次访问都必须真的读/写内存**，不许用寄存器里的缓存值。它的核心职责只有一条：禁掉编译器对该变量读写的优化。

#### 展开讲

**编译器优化为什么在这里是错的。** 常规优化逻辑：两次读之间没有写操作 → 值没变 → 第二次直接用寄存器缓存值。对普通变量这是提速，对"被外部力量修改"的变量这是灾难——值在程序不知情时已经变了。

**volatile 明确禁止的三类优化**

1. 禁止缓存到寄存器：每次读写都落到内存。
2. 禁止重排涉及 volatile 变量的指令（仅限编译器层面；CPU 乱序需要内存屏障，volatile 管不到）。
3. 禁止把对 volatile 变量的读写当"死代码"删除。

**两个典型战场**

- **硬件寄存器映射**：`volatile uint32_t* reg = (volatile uint32_t*)0x4000;` 硬件随时会改这个地址的值，不加 volatile，第二次读会被编译器直接优化掉。
- **ISR 与主程序通信**：主循环轮询 flag，中断服务程序里置 flag = 1。不加 volatile，编译器可能把 flag 缓存进寄存器，主循环永远读不到中断改的值。

**volatile 管不了的事**：它既不保证原子性，也不保证内存顺序。`volatile int i; i++;` 依旧是"读-加-写"三步，多线程竞争照样翻车。线程同步的唯一正确选择是 `std::atomic` 或锁。

#### 高频追问

**Q：volatile 能保证原子性吗？**
保证不了。它只是强制访问走内存，`i++` 仍是三步操作，两个线程可能同时读到旧值、各自加一、结果只加了 1。要原子性，用 `std::atomic`。

**Q：volatile 与 std::atomic 的本质区别？**
三条轴：原子性——atomic 有、volatile 无；内存序——atomic 可指定 memory_order 控制全链路顺序，volatile 只挡编译器重排、挡不住 CPU；用途——volatile 服务硬件交互与 ISR，atomic 服务线程同步。

**Q：volatile 和 const 能同框吗？**
能。`const volatile uint32_t* status_reg;` 表示"程序不许写（const），但值随时可能被硬件改（volatile）"——典型只读状态寄存器。

**Q：多线程里拿 volatile 顶替锁行吗？**
不行。既无原子性又无内存屏障，这是历史遗留的错误姿势。现代 C++ 多线程共享变量：要么 atomic，要么 mutex。

### 8. inline 与宏

**场景还原**：这道题的表层答案人人会背——"宏是文本替换，inline 是函数"。但面试官想听的是：宏的多次求值 bug 具体怎么炸、inline 一定会被内联吗、宏有什么是 inline 替代不了的。

#### 三句话版本

两者活在**编译流水线的不同阶段**：宏在预处理阶段做纯文本替换，无类型检查、无作用域、不可调试，还可能触发多次求值 bug；inline 函数在编译阶段处理，是正经函数——有类型检查、守作用域、可调试、参数只求值一次。一句话：宏是"无脑替换"，inline 是"带大脑的函数"。

#### 展开讲

**宏的致命伤：多次求值。** `#define SQUARE(x) ((x) * (x))` 平时看着没事，遇到 `SQUARE(a++)` 就展开成 `((a++) * (a++))`——a 被加了两次！这是文本替换的天然缺陷。inline 函数传参只求值一次，根本不存在这个问题。

**处理阶段差异**。宏在预处理期展开，此时编译器还没介入——它不懂类型、不懂作用域、不懂命名空间；宏定义还是全局的，`#define` 一旦出现就全文件生效，极易撞名。inline 函数走完整语义分析：类型检查、重载决议、模板实例化一样不少，且遵守命名空间与类作用域。

**调试体验差距**。宏展开后调试器看到的是替换后的产物，你无法在宏"内部"下断点；inline 函数即便真被内联，现代编译器的调试信息通常也能映射回源码行。

**宏仍不可替代的三个场景**：条件编译（`#ifdef`）、字符串化（`#` 把参数变字符串字面量）、令牌拼接（`##` 拼接标识符）——这三个能力只有预处理器有。

#### 高频追问

**Q：inline 函数保证被内联吗？**
不保证。inline 只是"建议"，编译器按函数体大小、有无循环/递归、优化级别自行决定：函数太大反而拒绝内联（避免代码膨胀）；没标 inline 的小函数在 -O2 下也可能被自动内联。现代 C++ 中 inline 关键字的主要价值其实是"允许在头文件里定义函数"（规避多重定义的链接错误），而非"强制展开"。

**Q：# 和 ## 怎么用？**
`#define STR(x) #x`：调用 `STR(hello)` 得到 `"hello"`。`#define CONCAT(a,b) a##b`：调用 `CONCAT(var,1)` 得到 `var1`。日志宏、断言宏、代码生成里常用，这是 inline 替代不了的。

**Q：现代 C++ 用什么替换宏？**
常量 → `constexpr`；类型安全的"宏函数" → inline 函数/模板；泛型操作 → 模板。但 `#ifdef`、平台适配、日志宏（要 `__FILE__`、`__LINE__`）这类场景宏仍是唯一解。

**Q：类内定义的成员函数默认 inline 吗？**
是。在类体内直接写实现的成员函数默认按 inline 处理，无需显式写关键字。但"是否真展开"依旧由编译器说了算。

### 9. auto 与 decltype

**场景还原**：简历上写了"熟悉 C++11"，面试官立刻掏出这题："auto 和 decltype 都能推类型，推导规则差在哪？什么时候选谁？"很多人答完"auto 自动推导"就卡住了—— decltype 对引用与 const 的处理才是真正的考点。

#### 三句话版本

auto 按模板实参推导规则工作：**剥掉顶层 const 和引用**（除非显式写 `auto&`）；decltype 按声明类型工作：**原样保留 const 与引用**。auto 只能用于变量声明（必须有初始化式），decltype 可作用于任何表达式。一句话总结：auto 是"我不在乎具体类型，你帮我推"，decltype 是"这个表达式是什么类型，一字不改地告诉我"。

#### 全维度对照

| 维度 | auto | decltype |
| --- | --- | --- |
| 推导机制 | 套用模板参数推导规则，丢顶层 const/引用 | 直接反映表达式的声明类型，修饰符全保留 |
| 引用处理 | 默认剥引用：`auto y = crx;` → y 是 int | 保留引用：`decltype(crx) a = x;` → a 是 const int& |
| 使用位置 | 仅变量声明，必须有初始化式 | 任意表达式，含函数调用、复杂表达式 |
| 典型场景 | 简化声明、范围 for、lambda 形参 | 返回类型后置、模板元编程、需要精确类型的场合 |

#### 高频追问

**Q：为什么 `decltype((x))` 推出引用而 `decltype(x)` 不会？**
decltype 对"变量名"和"表达式"是两套规则：x 作为变量名，直接给出声明类型；加括号后 `(x)` 变成左值表达式，decltype 对左值表达式统一推成 `T&`。括号一加，性质就变了。

**Q：模板元编程里各自强在哪？**
auto 强在"少写类型名"，代码可读；decltype 强在"精确取类型"，SFINAE、类型萃取这类编译期计算绕不开它。

**Q：decltype(auto) 解决什么？**
把 auto 的简洁和 decltype 的精确缝在一起——按 decltype 规则推导，不会像裸 auto 那样丢掉引用和 const。最典型用途是完美转发场景的返回值推导。

### 10. sizeof 与 strlen

**场景还原**：表层的"sizeof 算内存、strlen 算长度"人人会说。真正的分水岭在三处：对指针和数组结果一样吗？数组传进函数后 sizeof 还准吗？strlen 的复杂度是多少、放循环条件里会怎样？

#### 三句话版本

sizeof 是**编译期运算符**，依据类型信息返回对象占用的字节数（含 `'\0'`）；strlen 是**运行期函数**，从首字符遍历到第一个 `'\0'`，返回字符个数（不含 `'\0'`）。对 `char s[] = "hello"`，两者结果分别是 6 和 5——一个看类型，一个看内容。

#### 全维度对照

| 维度 | sizeof | strlen |
| --- | --- | --- |
| 本体 | 运算符 | `<cstring>` 里的库函数 |
| 执行时机 | 编译期 | 运行期 |
| 计算依据 | 类型/变量的字节占用 | 首个 `'\0'` 之前的字符数 |
| 是否含 `'\0'` | 含 | 不含 |
| 适用对象 | 任意类型 | 仅 `char*` / `char[]` |
| 复杂度 | O(1)（编译期确定） | O(n)（运行期遍历） |

#### 三个经典陷阱

**陷阱一：数组与指针不是一回事。** `char arr[] = "hello"` 的 sizeof 是 6（类型是 char[6]）；`char* ptr = "hello"` 的 sizeof 是 8（类型是指针，64 位下 8 字节）。strlen 对两者都返回 5——它只认内容，不认类型。

**陷阱二：数组传参即退化。** 数组作为函数形参会退化为指针，函数体内的 `sizeof(arr)` 拿到的是指针大小（8），不是数组大小。想在函数里知道数组长度，要么额外传长度参数，要么用模板推导。

**陷阱三：中间的 `'\0'`。** `char s[] = {'a','\0','b','c'}` 的 sizeof 是 4（数组真实大小），strlen 是 1（碰到第一个 `'\0'` 立刻停）。strlen 对"数组多大"毫无兴趣，只关心 `'\0'` 在哪。

#### 高频追问

**Q：把 strlen 写进循环条件会怎样？**
`i < strlen(s)` 会让每次迭代都重新扫一遍字符串，O(n) 循环直接劣化成 O(n²)。正确姿势是先缓存：`size_t len = strlen(s);` 再循环。

**Q：sizeof 结果一定是编译期常量吗？**
标准 C++ 里是的（C++ 不支持 VLA）。C99 的变长数组会让 sizeof 退化为运行期计算，但 C++ 没这个问题，所以 sizeof 可以出现在模板参数、数组声明等需要常量表达式的位置。

**Q：现代 C++ 还需要 strlen 吗？**
用 `std::string` 的话 `.size()`/`.length()` 是 O(1)（string 内部维护长度）。只有处理 C 风格 `char*` 才需要 strlen。现代 C++ 尽量用 string 避开整类问题。

### 11. 浮点数比较

**场景还原**："为什么浮点数不能用 == 比较？"——答"有精度问题"只值一分。追问"0.1 在二进制里长什么样""epsilon 取多大""绝对误差和相对误差怎么选"才是这道题的完整形态。

#### 三句话版本

IEEE 754 下，二进制浮点数**无法精确表示所有十进制小数**：0.1 在二进制中是无限循环小数，存储时必然截断，误差从"表示"这一步就产生了。运算中误差还会累积，所以 0.1 + 0.2 ≠ 0.3。正确姿势是用误差容忍度（epsilon）比较：判断两数之差的绝对值是否小于阈值，而不是判断严格相等。

#### 展开讲

**根源：二进制装不下所有十进制小数。** IEEE 754 单精度共 32 位：1 位符号 + 8 位指数 + 23 位尾数，尾数折算约 7 位十进制精度，超出部分一律截断。0.1 的二进制是 `0.000110011...`（0011 无限循环），存进 23 位尾数必然被截——误差不是运算错了，而是数字本身就没法精确表示。

**三种比较策略**

- **绝对误差**：`|a - b| < epsilon`。实现最简单，但 epsilon 固定：对大数失真（1000000.0 与 1000000.1 的差可能超阈值），对极小数过松。适合数值范围固定封闭的场景（颜色值 0~1、像素坐标）。
- **相对误差**：`|a - b| / max(|a|,|b|) < epsilon`。按比例衡量，大小数通吃；但 a、b 逼近 0 时分母爆炸，结论失真。适合数值跨度大的科学计算。
- **混合法**：先绝对误差兜住接近 0 的区间，再走相对误差——工程里最常用。

**常见浮点陷阱清单**

- 累积误差：循环里反复 +0.1，误差越滚越大
- 吸收：`1e20 + 1.0 == 1e20`，小数被大数吞掉
- 抵消：两个相近大数相减，有效位骤降
- 非结合性：`(a+b)+c` 与 `a+(b+c)` 结果可能不同

#### 高频追问

**Q：为什么 0.1 + 0.2 ≠ 0.3？**
0.1 与 0.2 在二进制里都是无限循环小数，各自截断、各带误差；相加后误差叠加，得到 0.30000000000000004。这不是 C++ 的 bug，所有 IEEE 754 语言（Java、Python、JS）一律如此。

**Q：epsilon 取多大？**
没有万能值，看业务精度：float（约 7 位有效数字）绝对误差常用 1e-5 ~ 1e-6；double（约 15 位）取 1e-9 ~ 1e-12；用相对误差时常取 `std::numeric_limits<float>::epsilon()`（约 1.19e-7）的若干倍。原则是按业务需求定，不是随手挑个"看着很小"的数。

**Q：什么情况下可以直接用 ==？**
极少数：比较整数值的浮点表示（`3.0 == 3.0`）、判断字面量赋值后的特定值（是否等于 0.0）、或两个值来自同一次赋值且未经历任何运算。只要过了加减乘除，== 就不可信。

**Q：NaN 有什么特殊性？**
NaN 是 IEEE 754 定义的无效值（0.0/0.0、sqrt(-1) 的结果），它跟任何值比较——包括自己——都返回 false。因此 `x != x` 是一种判 NaN 的野路子，规范做法是 `std::isnan(x)`。

### 12. 变量作用域与生命周期

**场景还原**：答"作用域不同"只是起手式。面试官接着会问：它们分别躺在内存哪一段？未初始化时值是什么？static 修饰全局变量改变了什么？静态局部变量何时初始化、线程安全吗？这四问对应三个分析维度：**作用域、生命周期、存储位置**。

#### 三句话版本

**局部变量**：定义在函数/代码块内，作用域限于本块，生命周期随栈帧生灭，住在栈区，未初始化时值不确定。**全局变量**：定义在所有函数外，作用域为整个翻译单元（extern 可跨文件），生命周期贯穿程序，住在数据段（已初始化）或 BSS 段（未初始化），默认零初始化。**静态局部变量**：定义在函数内、static 修饰，作用域锁在本函数，生命周期贯穿程序，住在静态存储区，仅在首次执行到定义语句时初始化一次。

#### 展开讲

**存储位置是最硬的区分**。局部变量在栈上：调用压栈、返回弹栈，快但短命。全局变量与静态局部变量都在静态存储区（数据段/BSS 段）：程序启动即分配、结束才释放。

**初始化规则差异**。局部变量不显式初始化时，值是栈上的残留垃圾——常见 bug 源。全局变量与静态局部变量不初始化时，编译器保证零初始化（整型 0、指针 nullptr、浮点 0.0）。静态局部变量只在首次执行到该语句时初始化一次，之后跳过——这正是单例模式的经典实现手法（C++11 起初始化线程安全）。

**static 修饰全局变量改变了什么**。不加 static 的全局变量是外部链接，其他翻译单元可以 extern 引用；加 static 后降级为内部链接，仅本文件可见，避免跨文件撞名。注意方向完全不同：static 修饰**局部**变量改的是生命周期，修饰**全局**变量改的是链接性。

**同名遮蔽**。局部变量与全局变量同名时，函数内局部优先；想访问被遮蔽的全局变量可用 `::globalVar`，但最佳实践是干脆不同名。

#### 高频追问

**Q：静态局部变量初始化线程安全吗？**
C++11 明确保证：多线程同时首次进入函数，只有一个线程执行初始化，其余等待。Meyers 单例（函数内 `static Singleton inst;`）的线程安全性正来源于此。

**Q：全局变量初始化顺序有什么坑？**
同一翻译单元内按定义顺序初始化；跨翻译单元顺序未定义（Static Initialization Order Fiasco）。若 A 文件的全局变量依赖 B 文件的全局变量，A 初始化时 B 可能还没就绪。解法：换成函数内静态局部变量（Construct On First Use），把初始化时机推迟到首次使用。

**Q：为什么"能用局部就别用全局"？**
全局变量的四宗罪：任何位置可改导致状态难追踪；跨文件依赖制造耦合；多线程访问需要额外同步；初始化顺序不确定。局部变量作用域最小、生命周期最短，最容易推理。

**Q：静态局部变量和全局变量都在数据段，差别在哪？**
存储位置相同，作用域不同：静态局部变量只能在定义它的函数内访问，编译器替你把关；全局变量（不加 static）可被其他文件 extern。从封装角度看，静态局部变量把"持久状态"关进了函数内部，更安全。

### 13. 四种类型转换

**场景还原**："四种 cast 有什么区别、什么时候用哪个？"——能报出四个名字的人很多，能讲清各自安全边界与底层机制的人不多，能解释"为什么 C++ 不学 C 用一个 (type) 搞定"的更少。

#### 三句话版本

C++ 用四个命名转换取代 C 风格 `(type)value`，意图是**让转换目的显式化，让编译器有能力帮你查错**：

- `static_cast`：编译期转换，用途最广，无运行期检查
- `dynamic_cast`：运行期转换，专攻继承体系的安全向下转换，失败返回 nullptr（引用则抛异常）
- `const_cast`：功能单一，只动 const/volatile 属性
- `reinterpret_cast`：最危险，比特位重解释，零检查

#### 展开讲

**为什么抛弃 C 风格转换？** `(type)value` 像一把瑞士军刀——什么都能干，但你看不出它此刻在干什么：它可能等价于上述四种中的任何一种，程序员与编译器都无法从代码里读出意图。四个命名 cast 是四把专用工具，意图明确，出问题好定位。

**static_cast**：编译期完成、零运行期开销。能做：基础类型转换（int→double）、`void*` 转具体指针、继承体系的向上转换（安全）与向下转换（不检查）。向下转错时它不拦你——直接未定义行为。

**dynamic_cast**：只服务带虚函数的继承体系。运行期靠 RTTI 核实对象真实类型：指针转换失败得 nullptr，引用转换失败抛 `std::bad_cast`。适用场景：手里只有基类指针、不确定实际指向哪个派生类、需要安全试探。

**const_cast**：唯一功能是加减 const/volatile。合法用途：去掉"底层 const"，比如变量本身非 const、只是被 const 指针指着，要传给一个参数不带 const 的旧 API。注意：对天生 const 的变量去 const 再修改是未定义行为。

**reinterpret_cast**：最底层最粗暴——把一块内存的比特按另一种类型重新解读，不做任何转换计算。用于指针与整数互转、不相关指针互转。99% 的应用层代码用不到，只有驱动、序列化、内存管理等底层才需要。

#### 高频追问

**Q：static_cast 与 dynamic_cast 向下转换的差异？**
static_cast 编译期完事、零检查，转错即 UB（读错内存、崩溃）；dynamic_cast 运行期经 RTTI 核实，转错得 nullptr 或异常，可恢复。代价是 dynamic_cast 有性能开销。

**Q：const_cast 去 const 后改值，何时安全？**
变量本身非 const、只是被 const 引用指着 → 安全；变量本身 `const int x = 42` 声明 → 未定义行为（编译器可能把 x 当常量优化，改了也无效）。

**Q：reinterpret_cast 与 static_cast 处理指针转换的本质区别？**
多重继承下 static_cast 会调整指针数值（基类子对象地址与派生类对象地址可能不同）；reinterpret_cast 一概不调整，比特原样重读，不关心类型关系、不保证结果有效。

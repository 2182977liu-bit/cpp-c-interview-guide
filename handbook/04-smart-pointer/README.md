### 1. 智能指针选型

**场景还原**：报出三个名字人人会，追问"什么时候用 unique_ptr、什么时候 shared_ptr"就开始含糊。这题考的不是定义背诵，而是**所有权语义**的理解深度。

#### 三句话版本

三种智能指针对应三种所有权模型：**unique_ptr 独占**（同时只有一个拥有者）、**shared_ptr 共享**（多拥有者靠引用计数协调）、**weak_ptr 观察**（不参与所有权，只"看一眼还在不在"）。选型原则一句话：能用 unique_ptr 就不用 shared_ptr，需要打破循环引用才用 weak_ptr。

#### 展开讲

智能指针的底层思想是 RAII：资源生命周期绑定对象生命周期，构造获取、析构释放，手动 delete 的泄漏风险被彻底清除。

**unique_ptr — 独占所有权**。同一时刻只有一个 unique_ptr 拥有资源；禁止拷贝、只许移动（std::move）；析构直接 delete；零开销，机器码与裸指针等价。90% 的场景应优先选它——函数内局部资源、类成员、工厂函数返回值。

**shared_ptr — 共享所有权**。多个 shared_ptr 指向同一对象，内部引用计数管理生命周期，最后一个析构时释放。代价：每次拷贝/析构都要原子操作计数，比 unique_ptr 重。只在确实需要多拥有者时用——缓存、观察者模式中的共享资源。

**weak_ptr — 弱引用/观察者**。不增加引用计数、不参与生命周期；经 lock() 尝试提升为 shared_ptr，对象已死则返回空。唯一用途：打破 shared_ptr 循环引用，或在不确定对象是否存活时安全"探测"。

**选型决策**：默认 unique_ptr；资源确实需要多处共享 → shared_ptr；出现循环引用或需要非拥有性观察 → weak_ptr。

#### 高频追问

**Q：unique_ptr 凭什么叫零开销？**
内部就是一个裸指针：无引用计数、无控制块、无原子操作。编译器优化后，unique_ptr 与裸指针生成的机器码完全一致。

**Q：shared_ptr 的代价具体在哪？**
两处：① 多一次控制块的堆分配（make_shared 可合并为一次）；② 每次拷贝/析构都要原子加减计数——高并发场景不可忽视。

**Q：循环引用怎么发生、怎么破？**
A 持 shared_ptr 指向 B，B 也持 shared_ptr 指向 A：两方计数永不归零、内存永不释放。解法：把其中一方改成 weak_ptr——不加计数，循环即断。

**Q：能用 unique_ptr 代替 shared_ptr 吗？**
能理清所有权链条（谁创建、谁拥有、谁销毁）时，绝大多数场景都能。shared_ptr 常是"懒得想所有权"的妥协品，用多了反而引入循环引用与性能问题。

### 2. 智能指针实现原理

**场景还原**："智能指针实现原理？"——答"RAII + 引用计数"只是第一层。追问"控制块里存了什么""weak_ptr 怎么知道对象死了""make_shared 为什么比 new 快"，能不能接住，决定这题的成色。

#### 三句话版本

智能指针本质是类模板：封装原始指针、重载 `*` 与 `->`，靠 RAII 在析构时自动释放资源。三种智能指针分别用独占所有权、引用计数、弱引用覆盖不同的生命周期场景。

#### 展开讲

核心思路：把裸指针包进栈上对象，利用析构函数自动释放堆内存——手动 delete 遗漏的问题从此消失。

**unique_ptr — 独占所有权的实现**。极简：delete 掉拷贝构造与拷贝赋值，只保留移动语义。同一时刻仅一个 unique_ptr 拥有资源，析构直接 delete。零开销，性能与裸指针持平。

**shared_ptr — 共享所有权的实现**。核心是**控制块（Control Block）**：存两个原子计数器——shared_count（强引用数）与 weak_count（弱引用数）。拷贝 shared_ptr 时 shared_count 原子加一；析构时原子减一；减到 0 释放资源对象。控制块本身要等 shared_count 与 weak_count 双双归零才释放。

**weak_ptr — 弱引用的实现**。与 shared_ptr 共享同一控制块，但不增加 shared_count。经 lock() 尝试提升为 shared_ptr：shared_count 已为 0 则返回空——对象已死。这就是它解决循环引用的原理：两个对象互相持 weak_ptr 不会阻止对方析构。

#### 高频追问

**Q：make_shared 比 new + shared_ptr 好在哪？**
`make_shared<T>(args)` 一次分配同时搞定对象与控制块（两者放同一块内存）；`new T` + shared_ptr 构造需要两次分配。少一次 malloc，缓存也更友好。

**Q：控制块何时释放？**
资源对象在 shared_count 归零时释放，控制块要等 weak_count 也归零才释放。所以只要有 weak_ptr 活着，控制块内存就一直占着——这也是 make_shared 的小代价：对象内存与控制块绑死，weak_ptr 不死，对象那块内存也收不回。

**Q：unique_ptr 能转 shared_ptr 吗？**
能：`shared_ptr<T> sp = std::move(up);`。反向不行。这是单向的所有权放大。

**Q：多线程下 shared_ptr 安全吗？**
引用计数加减是原子的、线程安全；但 shared_ptr 对象本身（指针值的读写）不线程安全——多线程同时读写同一个 shared_ptr 变量需要加锁。

### 3. 智能指针线程安全

**场景还原**："shared_ptr 是线程安全的吗？"——直接答"是"或"不是"都错。这题的得分点在于能否把"哪一层安全、哪一层不安全"分层讲清。

#### 三句话版本

一句话结论：**控制块线程安全，对象访问不安全，指针实例的并发写也不安全**。shared_ptr 的引用计数加减是原子操作，但它管理的对象和 shared_ptr 变量本身都需要你自己加锁。

#### 三层拆解

**第一层：控制块（引用计数）— 安全**。控制块用 std::atomic 实现计数加减：多线程同时拷贝、析构各自持有的 shared_ptr 副本，计数不会错。这是标准明文保证的。

**第二层：shared_ptr 实例本身 — 不安全**。同一个 shared_ptr 变量：多线程并发**读**没问题；只要有线程在**写**（reset、赋值、移动），就必须加锁——写操作要同时改内部指针和调整计数，不是一个原子步骤。

**第三层：管理的对象 — 不安全**。智能指针只管生命周期，不管对象内部的并发访问。多线程经各自副本访问同一对象，读写对象成员仍需 mutex 保护。

**unique_ptr**：独占语义，不存在共享场景；所有权转移（move）不线程安全，必须确保同一时刻只有一个线程操作它。

#### 高频追问

**Q：引用计数用什么内存序？**
加计数用 memory_order_relaxed 就够（无需同步其他数据）；减计数必须 memory_order_acq_rel——减到零要释放对象，得保证之前所有线程对对象的写入对当前线程可见。

**Q：怎么在线程间安全传递 shared_ptr？**
最简单：按值传参——拷贝时计数原子加一，各线程持独立副本、互不干扰。若要修改一个全局 shared_ptr 变量：C++20 有 `std::atomic<std::shared_ptr<T>>`；更早版本只能上 mutex。

**Q：多线程并发读同一个 shared_ptr 变量安全吗？**
安全。标准规定同一实例的并发只读访问不构成数据竞争；但只要有一个线程在写，所有访问都必须同步。

**Q：为什么不把 shared_ptr 整体做成原子？**
性能代价太大。绝大多数场景 shared_ptr 是线程局部使用的，每次操作都走原子指令纯属浪费。atomic<shared_ptr> 留给真正需要跨线程共享同一指针变量的场景，按需启用。
